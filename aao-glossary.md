## Abbreviations, conventions, and named laws · added at v2.7

**ECI.** Einstein Conversation Insights, Salesforce's native call-capture product. Its transcripts and its related-record stamp are inputs; the stamp is inference and never the answer. Roughly 75% of target customers have no ECI; their transcripts arrive as files.

**`altify-pbo`.** Altify's packaging org. Never read, under any circumstances, standing rail.

**OM_ / AM_.** The vendor's own label prefixes: opportunity-map and account-map variants of a question. AM_OM_ is shared wording. No single list is the ontology; per-map bytes differ.

**Inverted grading.** Matthew's ruled method: the system's output first, graded row by row; blank rows are the only channel for misses; findings state their nature ("three UNDERs found"), never a percentage.

**Stamp, head, fold.** Every document's version lives on a stamp line inside it, nowhere else; changelog heads accumulate newest-first at the top; a fold is the act of writing rulings from a session into the documents and bumping the stamps. Wrong text is marked wrong in place, never deleted.

**The silence law.** The system journals what happened, never what did not. No abstention rows at any grain; zero occasions writes nothing; the failure direction is silence, never spray.

**The failed-twice law.** Where an instruction has failed twice, change the structure so the wrong answer cannot be expressed; never write the instruction a third time.

**The two-halves law.** A version string must cover every input that can change the output it stamps, or it is decoration. Applied to charter prompts (prose plus declared contracts), and to normalization (normalizer version plus raw input hash).

**The parse law.** A mismatch between stages is our bug and throws; it is never absorbed, defaulted, or reported as model behavior.

**The capability law.** A capability claim is unverified until tried from the runtime that will make the call, including claims about our own code.

**CODE and design.** The two working roles beside Matthew: CODE is the builder session (a Claude Code agent operating a git repository with the sandbox connection; it reads the CODE inbox at every pickup, builds, runs, and ships run reports with row exports). Design is the architect session (this document set's author; argues structural decisions, folds rulings, verifies every export). Matthew rules methodology and grades output.

## Terms added at v2.6 · the loop era

**The iteration loop.** The working mode ruled by Matthew, 6 August: the CODE inbox is the standing channel across sessions; every run ships its row export, stage timings, governor consumption, and full regression disposition or it does not count as a report; design-side verification agents audit each iteration mechanically against the frozen artifact and the regression seed; Matthew grades judgment only; design defaults technical calls with both positions recorded, and Matthew's rulings settle methodology.

**The one-way scope halves.** Call 0's scope read after the failed-twice law retired the two-sided question: two independent questions, does this call carry opportunity content and does it carry account content, each answered yes-or-no with a byte-locating quote and a reason. DUAL is both yes; NEITHER is sayable and dispatches nothing; a missing side throws; a yes whose quote does not locate is worse than a no. A majority cannot eat a minority because no question asks for a majority.

**Routed-not-dispatched.** The journalled state of a grain that call 0 routed but the system declined to run: the account grain while backburnered, and the opportunity grain where the deal resolved NONE or AMBIGUOUS. Carries the yes-quote as its reason. Distinct from ran-and-found-nothing, and neither ships the other's export.

**Claim retirement.** The record law reaching the claim ledger: a wrong standing claim is marked retired in place with its reason, keeping its quote and verdict readable forever; replays exclude retired claims; retraction clears whatever map value the retired claim carried. Nothing is ever deleted. The trigger exception is one-way and describe-checked.

**Retraction.** What re-run does when a derivation empties: projection writes the current derivation including null, only where the watermark proves the value is ours and unmodified, and the retraction stamps its watermark like any write. A blanked vendor field reads identically to never-established; the note carries the difference.

**Occasion identity.** The conversation itself as a key: source-system reference plus occurred time, deterministic, never the normalization's bytes. One call arriving as any number of Source rows or normalizations is one occasion. Coverage counts occasions. Distinct from the artifact hash, which remains the byte-provenance key that spans verify against: two keys for two jobs.

**The identity alias.** The read-time join of one human's multiple participant rows on their resolved Contact, email then name-within-account, never-pick. Never a row merge, because claims key the Participant and a merge rewrites what claims point at. Two unresolved rows for one human stay visibly split.

**The composed normalizer stamp.** `NF1+raw:<hash>`: the normalizer version composed with the raw input's hash, per the two-halves provenance law, so two different byte outputs can never carry identical stamps. `NF1+out:` is the fallback where the raw was never recorded. Rows stamped before composition keep their uncomposed stamps permanently; the freeze list disambiguates them explicitly.

**The blank-retry guard.** One re-invocation of a family read that returned zero pairs while matching the cheap-blank signature (early return, small output). A second zero stands; both invocations are journalled. It never forces pairs; it refuses to accept a single cheap blank as a family's only look. Addresses the whole-family blanking mode of the recall problem, not the within-read miss.

**The freeze list and the training set.** The freeze list is the explicit, NF1-only, hash-named corpus of fixtures that gate 3 runs against; fixtures are taken from the list, never queried from the org. The training set is the fixture everything was calibrated against, named on the list so it can never be counted as unseen; its precision predicts nothing. Authored fixtures never substitute for customer speech.

**The refusal doctrine.** A law that only permits corrections it can prove safe will sometimes refuse one that is safe, and paying that cost is what makes the law worth having. Recorded after the schema's third proven-right refusal (raised-at immutability, the claim ledger's insert-only rule, the normalizer-version restamp).

## A. The atomic unit · gloss v2.1

**Proposition**
A statement about one opportunity that is either true or false and nothing else. The atomic unit of the entire system.

A proposition has no degrees. For a record-sourced proposition its text is never authored by us and never ships in the package; a schema-sourced guided question ships as our seed reference data, org-overridable. *Narrowed in v2.2.* It is read from the customer's org at runtime. See **Rubric Discovery**.

**Proposition Kind**
How a proposition can be established. Two kinds, and the distinction determines whether a model is involved at all.

| Kind | Established by | Basis | Evaluated by |
|---|---|---|---|
| **Evidence-established** | A span from a transcript, email, or note | Citation into the source | Model, then blind re-adjudication |
| **State-established** | A condition over post-write structured state | The state rows that satisfied it, each carrying its own citation | Apex predicate, or a model where judgment is required |

State-established does not mean model-free. *Does anyone on this map carry role Decision Maker with budget authority* is a predicate Apex evaluates, replayable and free. *Is the pattern of support across the buying committee sufficient* requires judgment. Both cite state rather than text; only the first costs nothing.

Either way the citation chain survives: the map row was established by a quote, and the proposition points at the map row. Follow it twice and you reach the words someone said.

This is why **Write Order** exists. State must be current at the instant Apex evaluates.

**Phase**
One of Altify's assessment groupings, for example *Is there an opportunity?* or *Can we win?* A container for propositions, not a proposition. Carries an implicit sequence and is therefore load-bearing for escalation timing. Values are org-configurable and read, not assumed.

**Gating Proposition**
A proposition whose falsehood is disqualifying. Business-facing synonyms, acceptable in customer material but not engineering artifacts: *necessary condition*, *do-or-die condition*.

**Verdict**
The system's resolution of one proposition at one moment. One of three **Verdict States**: `TRUE`, `FALSE`, `UNVERIFIED`.

> **`UNVERIFIED` names the slot, never a label to match.** *Ruled in v1.6.* The mirror value it writes to is whatever the org's own value set uses for its open position — *Unknown* in Altify's org, possibly *Unverified* or *Working On It* in another. The slot is identified structurally: by API value where Altify ships the value set, which survives relabelling, and by setup-time mapping where the org authors its own. **Never by matching label text**, which is the same discipline that already forbids keying on a question's title string.

**Establishment**
Evidence or state sufficient to move a proposition off `UNVERIFIED`, in either direction. Establishing `FALSE` is an establishment. A proposition is established or unestablished; never partly.

**A claim row is not the same thing as an establishment.** Every establishment is a claim row; not every claim row is an establishment. An `UNVERIFIED` claim carries a citation, records that the question was asked, and establishes nothing. *The write law's rule that an establishment requires a citation runs one way only, and always did.*

**Absence Never Establishes**
Absence of evidence never resolves a proposition to `FALSE`. `FALSE` requires a citable span asserting the negative. Where nothing has been found in either direction, the verdict is `UNVERIFIED`, however long that has been the case and however important the proposition.

> **Consequence, and it is the non-obvious part:** verdict state and flag severity are independent axes. Verdict state is epistemic and reports only what evidence supports. Flag severity is operational and reports urgency. An unanswered gating proposition can be red without ever being `FALSE`.

> **Corrected in v1.6, and it is a correction rather than a clarification.** Earlier versions of this entry read as though `UNVERIFIED` were the empty state. **It is not. Null is the empty state, and `UNVERIFIED` is an answer.**

**The three record states**
What exists in the record after one proposition has been considered. One writes a claim row; two write nothing, and they write nothing for opposite reasons.

| State | What it means | What is written |
|---|---|---|
| **Null** | Nobody has said anything about this proposition | **No claim row.** Nothing |
| **`UNVERIFIED`** | Somebody addressed it and it came back open — *I'm not sure who signs off on this* | **A claim, with a citation — and the answer it moves** |
| **Abstention** | The model looked and declined to commit | **Nothing.** No claim, no field change, no citation |

`TRUE` and `FALSE` are establishments and were never in question.

**Null**
No claim row. Includes the overwhelmingly common case: the evidence was read and does not bear on this proposition. A discovery call about integration architecture is silent on the signature process; that silence writes nothing, is not a failure of anything, **and is not an abstention** — see below.

**An `UNVERIFIED` claim carries a citation, like any other claim.** *Changed in v1.6 — extraction previously withheld the span on `UNVERIFIED`, which made an open answer indistinguishable from a question never asked.* The span asserts that the answer is open: *I'm not sure who signs off on this.* **A cited answer whose content is not yet known.** The answer it moved is overwritten the moment a better one arrives; the claim that recorded it never is, and it counts as work having been done rather than work outstanding. *Corrected in v2.0 — the old sentence said "it is overwritten", which was the naming defect speaking.*

> **It is a finding, not an establishment — and this is the one place the vocabulary must be exact.** **Establishment** keeps its meaning everywhere in the set: evidence sufficient to move a proposition off `UNVERIFIED`, and a cited `UNVERIFIED` does not move it. It **does not satisfy its condition and does not clear a flag.** Whether the work was done and whether the deal is safe are different questions, and this state is how the record answers the first without corrupting the second.

**No special name, and no inference over the mirror's label.** *Ruled in v1.6.* The state is `UNVERIFIED`; what distinguishes *asked and open* from *never asked* is the citation's existence — on the Answer, and in the note beside the projected qualifier status or assessment answer. The mirror value it projects to is a **slot, not a label**: *Unknown* in this org, possibly *Unverified* or *Working On It* in another. See **Verdict**.

**Abstention**
The model read evidence that bears on a proposition and **declined to commit.** It writes no claim, changes no value, carries no citation, and clears nothing. It survives only as a candidate-ledger row that retires to the decision log — visible where reasoning telemetry is read, invisible on every surface a seller works.

**Not sure is a first-class answer in Altify's own methodology** — the Political wizard offers it as a third option. *Sharpened in v2.1: this was always true and is now stated harder.* Abstention is built into the vendor's design, not imposed on it by ours.

> **The consequence, and it is why abstention must stay rare.** On the mirror, a proposition can be null because nobody discussed it or null because the model would not commit, **and those are indistinguishable.** A legibility problem rather than an accuracy one, and no field fixes it — only a low abstention rate does.

> **Abstention is not silence.** If *the transcript did not mention budget* counted as an abstention, the rate would be dominated by the ordinary case and would stop measuring the thing it exists to measure. **The charter output schema must separate bears-on-it-and-declines from does-not-bear-on-it** — and whether a model makes that separation reliably is unmeasured, so the schema must ask for it before anything can find out.

**The flag does not care which; the seller does.** Under **Day-One Red** a gating proposition's flag stands on null and on `UNVERIFIED` alike — a question nobody has asked is as dangerous as one that came back open. But *nobody has raised this* and *they do not know* require different next moves, so the distinction survives to the surface through the citation's presence, even though it never changes flag behaviour.

**[v2.5 note: within the pass (Charters §P8), abstention rows do not exist at any grain — the pass writes what happened, never what did not; the run receipt and one-for-one-for-one arithmetic are the completeness record. The three-record-states table above stands for the wider system and for pre-pass rows; the Abstention entry's candidate-ledger mechanics stand as history for rows that carry them.]**

**Citations Do Not Cross Deals**
A proposition is a statement about one opportunity. Evidence from deal A never establishes a proposition on deal B, even about the same person. History informs where to look and what to expect. It never establishes.

**Roll-Up**
Deterministic arithmetic over established verdicts. Not a verdict, carries no citation, never an establishment. `ALTF__Probability__c` is Altify's own roll-up. Roll-ups are the surface customers embed in briefs, rituals, and BI tools.

**Proposition Corpus**
Every proposition discovered in the org. Changes when the org's metadata or rubric records change, never when our package version changes.

**Live Set**
The subset of the corpus in scope for one opportunity at one moment. Assessment questions narrow by the **Applicable Set**; qualifiers narrow by sales process and stage; both then filter by prerequisites and existing establishments. *Corrected in v1.7 — the earlier sentence filtered both by sales process, which was never the assessment mechanism.* Resolved deterministically by Apex. No model participates.

## B. Rubric discovery · gloss v2.1

The mechanism that makes the package org-agnostic. Nothing here is optional.

**Rubric Discovery**
The runtime read of the customer's own metadata and records to produce the proposition corpus, the permitted output vocabulary, and the guidance text. Performed by describe and SOQL against the org, refreshed on a schedule. **The package ships no record-sourced questions** — no assessment criterion text, no qualifier text, no field names, no picklist values, no help text. *Narrowed in v2.2:* the schema-sourced ontology ships as our own seed reference data, org-overridable, because that text is unreachable from the runtime that needs it. See Guided Question.

This is what makes the system work in an org it has never seen, on an Altify version from 2012, with a rubric the customer rewrote last week.

**Proposition Source**

| Source | Discovered by | Example |
|---|---|---|
| **Record-sourced** | SOQL over rubric records | Assessment criterion text, sales process qualifier text |
| **Schema-sourced** | Describe over object fields | Relationship and insight map dimensions, from field label, help text, and picklist values |

Schema-sourced is the harder case and the reason dynamic Apex is required. The same logical dimension may carry a different label, different help text, and a different value set in every org, and the account-level map does not use the same dimensions as the opportunity-level map.

**The two mechanisms are not a stylistic split. They are a confirmed property of how Altify stores its own methodology.** Criteria and qualifiers are records, so they are read with SOQL. Map dimensions have no records at all, so they are read with describe. `ALTF__Translation__c` carries assessment criteria, qualifiers, account plan questions and quicklinks, and **does not reference map dimensions** — which is the confirming evidence, not an inference from field names.

**For a schema-sourced proposition, the field label plus the value set is the rubric.** Nothing else. There is no sentence to find, because Altify never wrote one.

> **Marked wrong in v2.1 — Altify wrote them.** Twenty-six guided questions plus the insight admission tests ship as **protected custom labels in `ExternalString`**: Support carries nine propositions, Political Status seven, Coverage three, and each insight type three or four. Enumerated by exact label on 2 August 2026; the localization overlay was queried and is empty in this org; the verbatim texts are in the charter-design record. **This raises a standard for the whole class**: schema-sourced propositions had been running on a field label while record-sourced propositions ran on verbatim authored text, and that asymmetry is closed. **Where an authored ontology exists, the guided questions are the propositions and the label names the dimension. Where none exists** — influence and conflict have no authored ontology; sixteen labels across both families and every one a UI string — **the label plus the value set remains the rubric**, exactly as the sentence above says, and the sentence is wrong only as a universal. See **Guided Question** below.

**The quiz vectors are not the rubric.** `_Answer__c` on a map dimension holds a semicolon-delimited path — `Yes;Yes;Yes;Yes;Yes` resolving to Mentor, `Not sure;Not sure` resolving to Unknown. That is a UI affordance that walks a human to a value. It is not the question, it is the wizard, and it must never be read as the proposition text.

A dimension with no `_Answer__c` field at all is a dimension Altify never built a rubric for. See **Scoped-Out Dimension**.

**Closed Vocabulary**
The set of values an extraction may emit for a schema-sourced proposition, generated at runtime from the org's actual picklist values. Never a hardcoded list. A value outside the discovered vocabulary is rejected by Apex before any write.

**Vocabularies are record-scoped or small-enum. Never org-catalogue-scoped.** Five insight types, five rungs on a ladder, six map dimensions, fifteen live propositions: all bounded by construction. A product or solution catalogue is not, and can run to six figures in an enterprise. Where a vocabulary would be a catalogue, scope it to the record instead. An opportunity's line items average under three; the catalogue behind them does not.

**Graceful Absence**
A dimension, field, or rubric record absent from the org produces no propositions. Never an error, a default, or an assumption. Version compatibility is achieved by feature detection, never version checks.

**Plan Type Source Field**
*Added in v1.7.* The Opportunity field that carries a deal's plan type, named — as an API-name string — by `ALTF__Opportunity_Plan_Type__c` on the Opportunity Manager Settings custom setting. An org choice: production names `Type`; the demo org names a custom category field. **Read per org per run, never assumed** — this org has zero Opportunity record types, and the field the pointer names is ordinary and mutable.

**Applicable Set**
*Added in v1.7.* The assessment questions in scope for one deal: the plan-type source field's value, matched by name against `ALTF__Opportunity_Plan_Type_List__c`, whose `AssessmentQuestionIds` codes select questions by `Name`. **Resolution mirrors the package, cell for cell**: a matched row with a populated list restricts to exactly those questions; an empty list, a null value, or an unmapped value resolves to every active question — filter semantics with an unrestricted default, observed in two orgs. A verdict lands only on the applicable set, or flags reference questions the seller's screen does not show. In production: seventeen questions for new-business plan types, thirteen for renewal, five shared, tiling the twenty-five active exactly.

**A code is not an identity.** Question `Name` values recycle across rubric generations — the prior generation was renamed *(migrated)* and its codes reissued — and across orgs. Identity binds to record Id and content hash. **And none of this is versioned by Altify**: the sales-process stamp covers qualifiers only, so the rubric snapshot — source field, scoping rows, question content, keyed by org Id, re-read and hashed every run — is the change detector.

**Resolution Route**
*Added in v1.8.* Every proposition resolves by one of three routes, recorded in rule data and reflected on the rubric snapshot: **P — predicate**, deterministic Apex over the discovered methodology graph, no model, always fill-dependent; **C — charter with state**, loop two reading the transcript and our committed rows together, citing rows when it cites state; **E — evidence only**. A route routes — it never establishes. Evidence can always arrive through loop one regardless of route, and an unanswered routed-computable proposition red-flags on the same clock as everything else. Per-proposition assignments live in Computable Share.

**Solicit Flag**
*Added in v1.8.* A flag on a proposition whose evidence is unlikely to surface passively — customer-internal facts, first-person internal actions — so it asks instead of waits: *tell me when you know.* Twelve of forty-four propositions carry it, and they are the written-clearing loop's first population.

**Proposition-State Snapshot**
*Added in v1.8.* The long-shape memory table: one row per deal per applicable proposition per change, carrying verdict, applicability and rubric version, derived from the journal and never written beside it. Exists because point-in-time pattern queries are the product. A question is a row value, never a column.

**Guided Question**
*Added in v2.1.* An authored proposition for a schema-sourced dimension, shipped by Altify as a **protected custom label**. Twenty-six exist. **The label is the identity; the text is the proposition; the localization overlay is the effective text.** **Sourcing RULED in v2.2 under LAW #1** (no dependency on any ALTF package version, ever): the text ships as our own seed custom metadata — a shipped default field and a subscriber override field, the reader preferring the override where populated — assumed universal, corrected per org at setup. Built and test-checked in the sandbox. See Section N item 14, closed.

**Capability Claim**
*Added in v2.1.* A statement about what the platform permits. **Unverified until tried from the runtime that will make the call**, never from whichever tool was convenient. Three design sentences were wrong in the same direction this sprint — Coverage as a frozen query, `required` on Source, and labels reachable by pattern query from Apex — and each was a true fact generalised to a place it did not hold. The ruling this term serves is Architecture's.

**Pattern Sweep**
*Added in v2.1.* The read discipline for label and metadata families: **sweep wider than the question, read the list, filter after.** Three ways a narrower read under-delivers, each observed. An iterator under-collects on sparse numbering — Support runs 1, 2, 4, 5, 6, 7, 11, 14, 16. A family pattern over-collects because sibling text shares it — `PRESSURE_EDIT_TYPES_HELP_TEXT` is edit guidance, not an admission test. And a targeted pattern under-collects because **the name may be misspelled** — the package ships `CONFCLIT_MODE_HELP_TEXT`, so `%CONFLICT%` misses it. **The discovery-filter-fault guard does not catch the third case**, because it fires on zero results and that query returned five.

## C. Evidence and context · gloss v2.0

Conflating these two is how the system produces a wrong answer confidently marked.

**Evidence**
Text a proposition may be verified against. Has a source, a timestamp, and an identified author or speaker. **Evidence may be quoted.**

**Context**
Prior state supplied to guide where to look. Current verdicts, existing notes, note age, note author, historical patterns. **Context may never be quoted.**

> **The rule:** evidence can be cited, context cannot. A verdict whose only support is context is not an establishment. It is `UNVERIFIED`.

**Evidence Item**
The portable shape all evidence is normalized into before anything reads it: text, source reference, timestamp, opportunity ID, author or speaker ID. A transcript turn, an email, and a note are all evidence items. Every stage downstream of ingestion operates on this shape and never a source-specific one.

**Source**
The artifact an evidence item came from, and the thing spans are verified against. Persisted in normalized form at ingestion. Normalization happens once and is versioned.

**Channel Independence**
Evidence channels are additive and none is required. A customer without activity capture still gets the system on transcripts. A customer without call recording still gets it on emails and notes. This is a consequence of the evidence item boundary rather than a separate rule, and it means no channel is ever a prerequisite for the product.

**Derived Classifications Are Read, Never Trusted**
Platform-derived labels are treated as hints, never as facts, and are always re-derived from primary data.

Two confirmed failures make the case. `speakerRole` labelled a company's own chief revenue officer as `EndUser`, because he had a Lead record rather than a User record: 41% of one transcript would have been ingested as customer evidence. `MeetingType` labelled an all-hands with zero external attendees as `EXTERNAL`.

Internal versus external is derived from the email domain on the participant. Buyer versus seller is derived the same way. Never from a platform label.

**Note Evidence**
One row per note offered as evidence: its text at the moment it arrived, its author, its arrival time, the opportunity, and where applicable the flag and proposition being answered. *Added in v1.3.*

**A note is a row, not a field**, and that is the whole reason notes are tractable. A narrative field accumulates, so polling one returns every sentence ever typed — meaning either every pass re-reads everything, or we own a diffing step whose output must be byte-stable because spans are verified against it. Rows have nothing to diff. New rows since the watermark, and the byte-stability problem never arises.

**Reconciliation Destination**
The one place we control that a response to a flag can be written to. *Added in v1.3.*

We do not control the surface a seller works on — it may be an MCP app, a Lightning component, a Flow, a third-party client with API access, or something that does not exist yet. **So we publish one destination and refuse to guess at any other.** Writing into our own object means our own trigger fires, which is what makes an express lane possible at all: the ruling against triggers on customer objects is precisely what made notes hard, and our own destination gives that back.

The accepted cost, stated rather than discovered: **a seller who types into the standard note field gets no express lane.** They are not ignored — the note poll picks it up on the slow clock — but the fast path requires the published destination, so **a flag must say where to answer it.** Otherwise the person who did the work in the wrong place sees the flag tomorrow and concludes the system does not work.

**Address**
The pointer from a piece of evidence to the flag or proposition a human was answering. Routing and priority only.

**An address is not a cause.** If the content establishes something other than what it was addressed to, **the content wins and the address is discarded.** A note written at the budget-holder flag may establish that somebody else is the real decision maker, clearing a different flag. Attempts key on the address; whether anything cleared keys on the journal.

**Attempt**
One arrival of evidence addressed to a flag. Countable, reportable, and **not** a claim that anything was established.

**Attempts count arrivals, not acts.** A seller who writes the same thing through the published destination and again as a standard note reads as two attempts. That is acceptable and must be named that way rather than called responses. It requires no matching rule, because the journal appends **accepted changes**: a second identical arrival moves no value, produces no receipt, and disappears on its own. The same evidence record is never read twice, which the evidence watermark already guarantees. **New evidence confirming what already stands is the other case, and it is different**: that writes a claim with outcome `Reinforced` and moves nothing — see **Claim**.

**Active Question Filter**
`ALTF__Active__c` on the assessment question. **88 questions exist in this org and 25 are active.** *Corrected in v1.7:* discovery reads active **and applicable** — active is the corpus filter, the Applicable Set is the per-deal filter, and neither substitutes for the other. Section headings are a picklist on the object rather than records, so phases are described, not queried. **Assessment Criterion and Altify Assessment Question are the same object** — one name is internal, one is the label.

**Answer Score**
`ALTF__Yes_Score__c`, `ALTF__No_Score__c` and `ALTF__Unknown_Score__c` — admin-set weights sized by how damaging each answer is. **This is the severity rubric.** `ALTF__Mandatory__c` on the assessment question is not: its own help text says it should be deprecated and is unused, and it is false on every row.

> **Severity is relative, never absolute.** Scores are org-defined, so a fixed cutoff flags everything at ±10 and nothing at ±1. Normalise against that org's own maximum spread. **And where Unknown Score is zero or null, fall back to No Score** — Altify's help calls zero typical, this org sets Unknown equal to No on every active question, so **this org is the atypical one** and a rule keyed on the declared cost of not knowing would fire on nothing in a normal install.

**Speaker Requirement**
The per-proposition rule stating who must have said something for it to establish. Held in the evidence contract. This replaces any notion of ranking sources by trust: a seller's note does not establish a proposition requiring buyer confirmation, not because notes rank lower, but because the seller is not the required speaker.

**A note is a seller assertion regardless of who typed it.** *Extended in v1.3.* Whether the seller typed it, dictated it, had an assistant write it, or had a colleague write it for them, the note was authored under their credential and carries their authority. Authorship is not ours to infer and we do not attempt to — every access model in use resolves authority to the authenticated identity, and so do we. **Read the words that are in the field.**

**A quoted third party inside a note does not become the speaker.** *Sarah told me the budget is approved* is a seller assertion about Sarah, not Sarah speaking, and it does not satisfy a requirement for buyer confirmation. Without this, quotation marks become a way to establish anything about the buyer from a seller's keyboard.

**Citation Is A Pointer, Not A Source**
A citation inside a note points at words in an original source. Extraction may follow the pointer to decide where to look. Re-establishment must cite the original source, never the note that quoted it. Otherwise a quote degrades through recopying and the byte comparison silently loses meaning.

**The Answer Re-Enters As Evidence**
A human response to a flag becomes an evidence item and enters through the same ingestion path as a transcript or email. Not a special case, not a side channel, not exempt from any check. This closes the loop: the seller's answer moves the bookmark, and the next pass reads it as evidence like anything else.

## D. Provenance and precedence · gloss v2.0

**Span**
An exact byte sequence copied verbatim from an evidence item. Byte-for-byte identical to the normalized source, including punctuation and encoding.

**Locator**
Where the span sits. Turn sequence number, character offset, record ID. A convenience for the reader and for narrowing the second pass. Never a substitute for a span.

**Citation**
Span plus source reference plus locator. **Every evidence-established verdict has one. There is no other basis.**

**Note Payload**
What the machine may write into an Altify note or comment field. **Exactly two things may occupy that field: a citation, written by the machine, and prose, written by a human.**

The machine writes citations only. Never prose, never summaries, never explanations, never a verdict paraphrased into a sentence.

> This is what makes the note safe to read on the next pass. Because the machine block contains only quoted evidence, there is no machine interpretation available to reinforce itself. Self-reinforcement is not prevented by a filter; it is prevented by there being nothing to reinforce.

**Receipt**
The persisted, immutable record of an accepted verdict: verdict state, citation, actor, charter version, timestamp. Never edited.

**A receipt is what a Claim carries. It is not a separate row and not a separate object.** The distinction that matters is the one below: the mirror upserts the present, the journal appends the past. A receipt lives on the appending side. Anything upserted — including the **Answer** — is a mirror row, and a mirror row is not a receipt no matter how identical its fields look. *Rewritten in v2.0. This entry previously said the object then called Claim was a mirror row and not a receipt. The boundary was right; the name made it unreadable, and the naming gap it tolerated is now closed rather than tolerated.*

**Actor**
Who or what produced a value. `MACHINE` with a charter and version, or `HUMAN`.

**Actor Stamp, And The Burden Of Proof**
A write is `MACHINE` **only if it carries a charter stamp.** Everything else is `HUMAN`.

The default runs this way because the failure is asymmetric. Misreading a machine write as human costs an overwrite we were entitled to make. Misreading a human write as machine destroys a person's judgment, which is the one outcome the system exists to prevent. The machine carries the burden of identifying itself.

**Actor Per Dimension**
**Our journal must supply the actor at dimension granularity. This is a hard requirement and there is no existing source for it.**

Human precedence operates per dimension: a human who sets Status must not lose Status, while Coverage on the same row stays machine-writable. Altify supports that resolution halfway. Each dimension carries its own `_Last_Modified__c`, so *when* is per dimension. But the only actor field is record-level `LastModifiedById`, so *who* is per row. One human edit to one dimension stamps the whole row, and every other dimension on it becomes indistinguishable from human-authored.

Two candidate sources were checked and both fail:

| Candidate | Why it fails |
|---|---|
| `LastModifiedById` on the row | Record-level. Cannot attribute one dimension of many |
| `ALTF__Log__c` | Records the page, not the record. Its Contact lookup is populated on **zero** of 6,630 opportunity-scoped Relationships edits, and no field names a changed record or field |

So the actor is ours to write or it does not exist.

**This does not create a backfill problem**, and the reason is the burden of proof above. Every dimension value written before this system runs carries no charter stamp, so it resolves to `HUMAN` and is protected. The default fails safe on exactly the population we cannot attribute.

**Human Precedence**
A value authored by a human is never overwritten, modified, or demoted by this system. Not on day one, not after three years, not when the evidence is overwhelming. There is no staleness rule and no expiry.

**Channel is irrelevant.** A judgment entered in the Salesforce UI, in a headless assistant session, through MCP, or through the API is a human judgment if a human authored it. The interface it arrived through carries no weight.

Where the machine disagrees with a human value, the only action available is a contention flag. Disagreeing in writing is the strongest thing it is entitled to do.

## E. Model roles and the checks · gloss v2.1

**Charter**
The standing, versioned definition of one model role's job: what it may read, what it must emit, what it may never do, and the schema of its output. Prose plus a schema. Not data, not per-customer.

A charter's *questions and permitted values are injected at runtime* from rubric discovery. The charter defines the job; the org defines the content.

**The model roles.** *Restructured in v2.1 — the table below listed six while this file itself defined eight: Insight Contention (Section K) requires a model and was absent, and Rule Discovery (Section F) is a weekly model pass and was absent. Both now appear. The old six-row table is superseded by this one rather than kept beside it.* Four evidence roles, one configuration role, one shared judge, one scheduled contention role, one library role:

| Role | Reads | Job |
|---|---|---|
| **Relationship** | Evidence | Person dimensions from evidence |
| **Insight** | Evidence | Insight cards from evidence |
| **Link** | Evidence | Person to insight, influence, and conflict. Separate because neither single-entity charter naturally emits claims about pairs. **Unbuilt — no authored ontology exists for influence or conflict, so this one is authored by us from zero. Open, Section N** |
| **Assessment** | Evidence and maps | Evidence-established propositions only. State-established ones are Apex |
| **Persona Derivation** | **Configuration** | Which propositions require a person, and which persona. Reads the rubric, never evidence. *Named the Role charter until v2.1 — retirement argued under Setup-Time Inference below* |
| **Re-adjudication** | A candidate | One charter, shared by all. Blind by design, so it does not need to know where a candidate came from |
| **Insight Contention** | A verdict and the person timeline | Semantic contention over unstructured content. Runs on a schedule, never in the write path. Defined in Section K |
| **Rule Discovery** | The decision log | Weekly pass proposing new contention types and non-establishment rules for a human to promote. Defined in Section F |

> **The naming decision is open and it is Matthew's.** The first four rows carry this file's names — Relationship, Insight, Link, Assessment — while the working documents use People, Problems, Politics, Process for the same four roles. **One must win**; the recommendation on record is this file's, since it is authoritative for vocabulary, with the working names recorded as accepted synonyms rather than left to drift. Until ruled, the working names are synonyms under debate, not vocabulary. Section N carries it.

Charter count is not a cost decision. Four reads of a 7,000-token transcript is roughly $0.28 against $0.21 for three. Optimise for output-schema coherence and attention, never call count.

**Setup-Time Inference**
The class the Role charter belongs to, named in v1.6 because there are now four of them and building four one-off mechanisms would be the mistake.

**One shape: a question about the customer's rubric that no schema answers, resolved by a model once per sales process, proposed rather than applied, ratified by a human, cached, and re-run only when the rubric version moves.** The output is rule data. It carries no citation, never enters the journal, and is never computed per deal.

| Instance | The question it answers | Status |
|---|---|---|
| **Persona derivation** *(the Role charter, until v2.1)* | Does this proposition require a named person, and which persona | Specified |
| **Computability** | Is this proposition state-established, given what this org actually populates | Added in v1.6 |
| **Qualifier-to-condition** | Which stage qualifier gates which methodological condition | Open — the mapping object was read and does not hold it; the mapping charter is the path |
| **Criterion-to-question** | Which assessment propositions the decision criteria feed | Open — Altify couples these by title string and we may not |

> **The reason to name the class rather than the instances.** Each of these was discovered separately and each looked like a one-off. Four instances of one shape is an argument for building the mechanism properly — one proposal surface, one ratification surface, one cache, one rubric-version dependency — rather than four charters with four review screens. *Whether it is literally one charter with four output schemas or four charters sharing one lifecycle is an implementation call and is not settled here.*

**Persona Derivation**
*Named the Role Charter until v2.1, and the old name is retired — the mechanism is unchanged.* **It writes exactly one field, `AAO_Required_Map_Role__c` on the Evidence Contract, whose sole reader is ghost seeding, answering from the persona vocabulary.** That is persona derivation — not Buyer Role and not Decision Orientation — and *Role* collided with a different axis, since Buyer Role is a dimension the evidence charters establish. Retire the name; keep the mechanism. Retired Terms carries the row.

The one charter that reads configuration rather than evidence, and the only one whose output a human ratifies before it takes effect.

For each proposition in the **full rubric**, it asks whether satisfying that proposition requires a named person, and if so which role, answering from the discovered persona vocabulary. It runs **once per sales process**, not once per opportunity and not once per evidence item — roughly twenty-five binary questions, cached indefinitely, re-run only when the rubric changes.

> **Inference over configuration is a different risk class from inference over evidence.** A wrong answer here is caught once, in review, by a human reading a list of twenty-five rows. The same wrongness in an evidence charter would be painted silently onto every opportunity in the org. This is why the Role charter is permitted to infer at all, and why its output is cached rather than recomputed.

Its output is the **required role set**, which is configuration, not a verdict. It carries no citation and never enters the journal.

**Required Role Set**
Ours, and persisted. One row per proposition per sales process: does satisfying this proposition require a named person, and if so in which role. *Clarified in v2.1:* the values are **personas**, drawn from the persona vocabulary, and the physical home is one field — `AAO_Required_Map_Role__c` on the Evidence Contract, per the single-destination rule in Section F. Its sole reader is ghost seeding.

**It must be an object rather than shipped metadata**, because it is derived from the customer's own rubric at runtime and ratified by a human in their org. Nothing about it can be known at package time. It is versioned against the rubric version that produced it, and re-derived only when that rubric changes.

**Loop Order**
Extraction runs as **two sequential loops per opportunity**, never in parallel.

1. **Loop one, the political situation.** Relationship, insight, and link. Commits the maps.
2. **Loop two, the assessment.** Reads the transcript *and* the maps loop one just committed. Commits verdicts.

The order is an invariant, not an optimisation. An assessment proposition can cite a map row, so the map must be current at the instant it is read. A stale map produces a verdict about a political situation that no longer holds.

**Admission Gate**
A set of cheap deterministic checks run against an evidence item before any charter reads it. Failing any gate means the affected charter **abstains**.

For a call, three gates:

| Gate | Signal |
|---|---|
| **Deal-scoped** | The call's related record is an Opportunity, not an Account |
| **Counterparty present** | At least one participant on a non-internal email domain |
| **Bounded committee** | Participant count below the cardinality guard, and external domains below a small ceiling |

Domain diversity is the strongest signal. A genuine buying committee comes from one company, occasionally two with a partner or consultant. Anything spanning many domains is an event, not a deal conversation.

For an email the same three questions apply against different fields: recipient count, domain diversity, and whether the message carries an opportunity key.

**Gates Are Per Charter, Not Per Transcript**
This is the part that matters. A customer executive stating a real pressure on stage at a town hall is genuine evidence about that company. What the attendee list is *not* is a buying committee.

So on a gated call the **relationship charter abstains while the insight charter proceeds**, and assessment proceeds too, because it reads the transcript and the maps rather than the roster. Abstain on the claim that cannot be supported, never on the whole document.

**Attendance Is Not Evidence Of Position**
A silent attendee produced no span, so there is nothing to establish about their role, status, or political standing. At most, attendance establishes coverage, and only on a call that passed the gates.

**Extraction**
Model pass one. Reads the live set, the evidence, and the context. Per proposition the evidence bears on, emits a verdict **and a citation — on `UNVERIFIED` too** — or an abstention, which emits nothing. Propositions the evidence does not bear on are simply not addressed, and the output schema keeps that distinct from abstention, or the abstention rate measures nothing. Writes to the candidate ledger only, never to the mirror.

> **Changed in v1.6.** This previously read *emits a verdict and, where the verdict is not `UNVERIFIED`, a citation.* **The span is now emitted on `UNVERIFIED` as well** — it is what distinguishes a cited open answer from null — and byte verification runs on it exactly as on any other span, so the state costs no new machinery.

**Span Verification**
Deterministic Apex. Byte comparison of the emitted span against the normalized source. Not a model. No error rate. Runs before the second model pass, so no model time is spent on fabricated spans. **[v2.5 note: the check catches invented words and cannot catch shortened ones — a cut prefix of a real quote is still a substring. Named as a live blind spot at adjudication sheet v0.7; grade-against-stored-spans is the defence.]**

**State Verification**
Deterministic Apex. Field-value comparison confirming that a cited state row actually carries the value the model claimed. The counterpart to span verification for state-established propositions. Also free, also zero error rate.

**Blind Re-adjudication**
Model pass two. Receives the proposition and its cited evidence. Receives neither the first pass's verdict nor any context. Adjudicates fresh. Never writes.

**Blind re-adjudication gates the write.** A verdict that fails it never reaches the mirror. It is not an auditor reviewing values that already landed.

**The four checks**
Span or state verification catches fabrication. Blind re-adjudication catches real evidence that does not establish the claim. The write law catches collision with human input. Historical contention catches a claim conflicting with what is known about the people involved.

Each catches a different failure and none substitutes for another. Only the last runs after the write, because it requires the journal to have streamed to memory.

## F. Rule data · gloss v2.0

**Evidence Contract**
Per-proposition data defining what would establish it. Data, not prose. Versioned. Carries: qualifying-evidence definition, speaker requirement, required role, prerequisites, whether the proposition is gating, **proposition kind**, escalation threshold or inheritance, truth-decay class, **`requires-ratification`**, and known non-establishing patterns.

The customer's own `Help` and `Tip` text is the first draft of the qualifying-evidence definition, authored by the people who own the methodology, and read at runtime rather than shipped.

**It is the single destination for everything derived once from the rubric and ratified by a human.** Required role, proposition kind and `requires-ratification` all land here rather than each acquiring an object, and every one of them is derived by the same shape of setup-time pass. *See **Computability**, and **Setup-Time Inference** in Architecture.*

**Computability**
Whether a proposition can be established by an Apex predicate over structured state rather than by a model reading a span — the **proposition kind** attribute on the evidence contract, and **it is derived, never assumed.**

**Classified by inference over configuration, never over a deal.** Run once per sales process, proposed, human-ratified, cached, re-run when the rubric changes. Same risk class and same mitigation as the **Role Charter**: wrong once, caught in a review of twenty-five rows, rather than painted silently onto every opportunity.

> **Computability is not a property of the question alone. It is the question plus whether that org populates the field.** *Decision team named* is computable only where Buyer Role is filled, and Buyer Role is blank on 45 of 166 opportunity-scoped map rows in Altify's own org. **The classifier must check the data and not only read the sentence**, or it marks propositions computable that quietly always return false — which is *Absence Never Establishes* violated by a classifier rather than by a charter.

**Truth-Decay Class**
A per-proposition property stating whether an establishment is permanent or revertible, and if revertible, what reverts it. **Three values.**

| Value | The proposition is | Loses standing when | Example |
|---|---|---|---|
| **Event** | About something that happened | **Never.** An event does not un-happen, and later silence says nothing about it | *The customer confirmed budget on 12 March* |
| **Standing** | A predicate over how the deal stands now | The underlying state moves | *At least one supporter at decision-maker level or above* |
| **Decaying** | Either, but its force fades | Age alone, with no event | An establishment whose currency the evidence contract bounds |

**Defaults by proposition source, requiring no configuration:**

| Source | Default | Rationale |
|---|---|---|
| Sales process qualifier | **Event** | A verifiable outcome that occurred cannot un-occur. A contract sent stays sent |
| Assessment criterion | **Standing** | A state of the world can change under you. Access to funds can be withdrawn |

Per-proposition override remains available in the evidence contract and is unnecessary in the common case.

> **Nothing changes from nothing, and a standing proposition therefore does not decay silently.** *Added in v1.6.* It flips only because the underlying rows moved, and rows move exactly two ways: **our own cited write**, which loop two reads in the same pass it was committed; or **a human editing the record directly**, which the `SystemModstamp` poll already returns. Both are observable, neither needs a new mechanism, and neither needs a trigger. Placement is in Architecture.

> **A note on two terms that collided, and were merged rather than both kept.** *v1.6.* An event-versus-state distinction was proposed as a new pair of terms. It is this property under a second name, so it is folded in here rather than added beside it. **The word *state* was also unavailable**: **State-Established** already names a different axis — *how* a proposition is established, by Apex predicate rather than by a span — and the two are independent. A standing proposition can be evidence-established, and an event proposition can be state-established. **Standing** is the value name for that reason.

A clarification that avoids an argument later: if the executive who made a connection leaves the company, the connection still happened. What decayed is whether it is still *sufficient*, and sufficiency is a different proposition with its own verdict.

**Non-Establishment Rule**
A recorded pattern that superficially resembles an establishment but is not. Accumulates from observed false positives. Versioned, never deleted.

**Rule Discovery**
A periodic model pass over the decision log looking for patterns that should become new contention types or non-establishment rules. **Runs weekly, never in the write path.** Its output is a *proposed rule* for a human to review and promote, not a flag and not a verdict.

This is how the system learns contention types nobody anticipated without putting an unbounded model call in the hot path.

## G. Persistence and the write law · gloss v2.0

**Candidate Ledger**
The persisted object holding proposed verdicts between extraction and commit. One row per candidate, carrying the proposition, the proposed verdict, the citation, the charter and version, and its verification state.

An object rather than a variable for three reasons. Model calls are callouts and cannot share a transaction with the write, so the pitch must survive between queueable links. Verification passes or fails per row, and that state has to be addressable. And a chain that dies at re-adjudication resumes from survivors rather than paying for extraction again.

Both loops share one ledger, discriminated by charter.

**Answer**
The current-state row for one question on one subject. Upserted, uniquely keyed, one per question per subject. The target of human precedence, the source of every projection, and the row a seller reads. It carries the accumulated quotes, so reconciliation months later reads a hot row with the words on it rather than replaying history. Holds only `TRUE` / `FALSE` / `UNVERIFIED` — abstention writes nothing, and a decline lives on the Candidate and nowhere else.

*Added in v2.0. This row was previously called Claim, which put the sentence "a claim is overwritten" into the design — wrong in plain English, since a claim is one assertion, made once, by someone, on the strength of something. See Retired Terms.*

> **Collision discipline.** Altify's assessment answer is `ALTF__Answer__c`; ours is `AAO_Answer__c`, and the records are distinct, but the word is overloaded in conversation. In anything written or said to Altify: *our answer row*, or *the assessment answer*. **Never bare *answer*.**

**Claim**
One establishment, from one piece of evidence, never edited. Insert only — no update, no delete; claims leave core only by retirement to the library. Carries what the answer was before and what it became, this claim's quotes and coverage, the interpretation used, the actor, the charter and rubric version, **the four keys** — opportunity, account, external person, internal person — **both clocks** — evidence-occurred and recorded-at — and **subject identity in the same form Answer uses**. One claim rests on one Source.

> **Replaying claims in evidence-occurred order must reconstruct every answer exactly. That is the exit test.**

**Progress is visible because claims never move.** Claim one says the answer went to `UNVERIFIED` and says that forever. Claim two says it went to `TRUE`. The answer says `TRUE`. All three are readable at once, and the delta between claims is what a brief or a retrospective reads.

**Outcomes:** `Established`, `Reinforced`, `Downgraded`, `Demoted`. New evidence confirming something already standing writes a claim with outcome `Reinforced` and moves no answer value — and it must, because guidance orders a person's criteria by what they have pressed most recently and most often, which is a count of exactly these rows. The same evidence arriving twice writes nothing; the evidence watermark stops it being read again.

**No claim-to-claim parentage.** Claims that bear on the same question relate by sharing an answer, which is a subquery, not a hierarchy.

*Rewritten in v2.0. Claim previously named the upserted current-state row — now the Answer — and Journal Event carried what this entry now describes. Journal Event is retired as an entity; its keys, clocks and subject identity moved here unchanged, and nothing it carried is lost.*

**Claim Basis**
What a claim rests on beyond its own quotes. A junction, master-detail to Claim. A claim citing state must name the row and quote its value, because the cited row will be edited afterwards and a citation that only points is a citation that rots — that rule existed before this object and had no home. This is the home.

**Half frozen, half live.** The snapshot of what the cited row said sits in immutable fields on the junction; the live record comes through the lookup; one subquery returns both, so a claim can show that a qualifier read *unknown* when the claim was written and reads *known* today. It may point at map rows, insight cards, decision criteria, **other answers**, **qualifier statuses**, and shadow people, and **each row names which part of the proposition it covers** — which is what makes partial coverage queryable rather than buried in JSON, and what a flag reads to say *here is what already stands, and here is the piece still missing*.

> **It records what was cited, not what was available.** A junction pointing at six types and freezing state is exactly the object that becomes a general-purpose context dump, and a claim listing everything on the deal reads as far better supported than it was. If a row cannot name which part of the proposition it covers, it does not belong on the claim, and this junction never authorises scanning the deal.

*Added in v2.0.*

**Mirror**
Current-state records. Upserted. Answers *what is true now*. Includes Altify's objects and our own — **our row on this side is the Answer.** Roll-up fields live here, recalculated on write.

**Journal**
The appending side of the design, and the name for the claim history collectively — concretely, the Claim rows. Never updated, never deleted. Answers *what happened and when*. Nothing subscribes to it; it is written history, not a message bus. *Rewritten in v2.0 — the journal is no longer a second row recording the same event; it is the claims themselves.*

> Mantra: the mirror upserts the present, the journal appends the past.
> **The journal is born on core and retires to the library.**

Every claim is an event by construction: person or proposition, opportunity, what changed, citation, timestamp, actor. This shape is why the claim, and not the answer, is what streams to memory.

**Roll-Up Record**
One record per opportunity, upserted, carrying the current operational state of the deal in our terms. Distinct from **Roll-Up** in Section A, which is arithmetic over verdicts. This is the object that arithmetic lands on.

**It hangs off the standard Opportunity, not the Altify Opportunity.** The standard record is the only parent both halves of the methodology share: verdicts hang off `ALTF__Opportunity__c`, maps hang off `Opportunity`. Hanging our roll-up off the Altify record would make it invisible for every deal not yet Altify-ised, which is precisely the population that matters at baseline.

**It is not a snapshot.** Upserted, not appended. See the retired term *daily snapshot*: a third copy written daily regardless of change is waste. Trend comes from streaming this record to Data 360, where each arrival is an event.

**It is derived, so it sits outside the write law.** No citation, no actor, no human precedence, no demotion. Nothing here is an establishment and nothing here may be cited. Rebuilding it from the mirror and the journal must always produce the same values, and if it ever cannot, the field belongs somewhere else.

**It carries only what Altify does not already carry.** `ALTF__Opportunity__c` already holds 109 fields including six pillar scores, six freshness stamps, uncovered key role counts, and PRIME action throughput. Duplicating any of it creates two numbers that disagree by the end of the quarter.

| Field | Why it cannot come from Altify |
|---|---|
| Red, yellow and green flag counts | Flags are ours. Altify has no flag concept |
| Contention count | Contention is ours |
| Missing persona count | Graduation is a live join, so Altify never records that a gap existed |
| Since-last-seen bookmark | Operational position in the evidence stream |
| Oldest unaddressed red flag age | Requires flag lifecycle, which begins with us |

**Decision Log**
Everything the model thought, including candidates that were rejected, abstentions, and why a contention fired. Separate from the journal, and separate on purpose.

The journal is the audit trail a customer's security team will inspect to answer *why does this record say this*. If most of its rows were rejections it would stop serving that purpose. The decision log is product telemetry: charter tuning, threshold calibration, rule discovery, and analysis of which contentions proved valuable. The candidate ledger is its source, and it retires to the library rather than being purged. **It has a memory table of its own — the seventh, ruled 31 July.** Earlier versions designated it for the library with no table among the six; complete candidate logging was ruled conditional on retrospectives being able to read it after retirement, so it gains one. Engagement category, evidence-occurred clock — **a stream's category and clock lock at creation, so this is decided rather than discovered.**

**`ALTF__Log__c` is not this and does not overlap it.** Checked, and the name is the only thing they share. Altify's log records that a user opened or edited a named screen, carrying a page, a type of View or Update, and the parent record — and no field anywhere on it names a changed record, a changed field, or a before and after value. It is attention telemetry. Ours is reasoning telemetry. Neither can be derived from the other.

**Link Rows**
Deal-scoped relationships: person to insight, and influence from one person to another. Each carries its own receipt, because a link is a claim.

Insight to person is many-to-many in two senses, who said it and who owns it, and some insights have neither. Those anchor to the opportunity and the account instead.

**Run Ledger**
Operational state only: per-deal bookmark, attempt counts, retries, dead letters. Not evidence, not deal history. Purgeable.

**Write Law**
The invariants enforced at the object level by Apex triggers, so every writer is governed identically whether it is this system, an integration, an API call, or an assistant. **Not configurable, not implemented in Flow, not editable by an administrator.**

The invariants: an establishment requires a citation; a span is byte-verified and a cited state row is field-verified; blind re-adjudication is blind; human-authored values are never overwritten or demoted; abstention is always available; emitted values fall inside the discovered vocabulary.

**Opportunity Stamp**
Every methodology row the machine creates carries its opportunity, enforced in the trigger rather than the charter.

On both `ALTF__Insight_Card__c` and `ALTF__Contact_Map_Details__c` the opportunity field is optional in the schema but not optional in meaning: **a row without an opportunity is an account-level record.** Omitting the stamp silently pollutes the account map for every customer.

Consequence, accepted deliberately: a company-wide truth learned on a deal is still deal-stamped and never rolls up to the account map in core. The account view comes from the journal stream in memory, where every row carries the account key regardless.

**Cardinality Guard**
Every deterministic creation path carries an upper bound. **Exceeding it means abstain and flag, never proceed.**

Determinism guarantees the system will not create something *wrong*. It does nothing to prevent creating something *absurd*, and absurd output destroys trust as fast as incorrect output. A two-hundred-person webinar must not produce two hundred map entries. A fifteen-thousand-line CPQ quote must not produce fifteen thousand solution cards. A three-hour discovery session must not produce ninety insight cards.

Where the bound is exceeded, the correct output is a flag saying a human must scope this, which is abstention applied to a creation path rather than to a verdict.

**Write Order**
Three legs, enforced per opportunity and never as a global barrier:

1. The relationship mirror commits first
2. The claim streams to memory
3. Historical contention reads memory, **excluding this opportunity**

Political state must be current when an assessment verdict is checked against it, or contention is evaluated against stale politics and the check is worthless.

**Autonomy Level**
The one genuinely configurable dimension of write behaviour.

| Level | Behaviour | Intended for |
|---|---|---|
| 1 | Human ratifies before every write | Least AI-mature orgs. Expected to be abandoned quickly |
| 2 | Human ratifies only writes that would produce a red flag | The practical default |
| 3 | Human ratifies **only contention** | Mature orgs |

Autonomy level changes *when a human is asked*. It never changes what the checks are, and no level permits a write that failed one.

**At every level, state-established claims and decision criteria commit live** — the levels govern the model-established remainder. *Amended in v1.6; see Ratification.*

Level 3's trigger is contention, and only contention: machine against human, or machine against history. Everything else accumulates as flags and clears through evidence, because a red flag on unconfirmed budget clears when someone says on a call that budget was approved. Nobody dismisses it; evidence retires it.

## H. Memory and the library · gloss v2.0

The Data 360 side. Where the fourth dimension lives.

**DLO, Data Lake Object**
Where ingested data lands before modelling. One per data stream.

**DMO, Data Model Object**
The modelled, queryable shape. Multiple DLOs commonly map into one DMO, and that convergence is the point.

**DMO Category**
Every DMO is **Profile**, **Engagement**, or **Other**, and the choice is load-bearing:

> **Profile DMOs overwrite. Engagement DMOs accumulate.** Profile describes who someone is. Engagement is time-series behaviour keyed on an event timestamp. Categorising a stream of events as Profile tells the platform to overwrite history instead of accumulating it.

A DMO inherits its category from the first DLO mapped to it, and afterwards only DLOs of that category may map. **This cannot be changed.** Wrong category means delete and rebuild.

**Individual**
The standard Profile DMO representing a person. Kept standard so identity resolution and the Customer 360 wiring are inherited rather than rebuilt. Joined on the real ContactId. **Data 360 identity resolution stays off**; the join is deterministic.

Consequence worth knowing: the timeline is *a person at an account*, not a person. Someone who changes employers gets a new Contact and a fresh timeline, and conglomerate structures split one human across timelines.

**Claim, in memory**
The custom **Engagement** DMO holding one row per claim, sourced by streaming core Claims. This is the timeline. It is not fields on Individual, because fields on a Profile DMO are current state and would be overwritten. *Retitled in v2.0 — this entry was Journal Event, retired as an entity by the Answer / Claim correction. The stream's shape is unchanged, because the keys, clocks and subject identity moved onto Claim intact.*

**Each row carries four keys, two clocks, and subject identity.** *Corrected in v1.3. Earlier versions of this entry said three keys and no subject identity, and were wrong.*

| Carried | What it is |
|---|---|
| **Four keys** | Opportunity, account, external person, internal person. A grain not recorded is a grain that cannot be declared later without reprocessing the corpus, which means re-paying every model call |
| **Two clocks** | When the evidence occurred, and when we processed it. Without both, a backfilled 2024 transcript collapses onto today and the whole trend is worthless |
| **Subject identity** | Which answer the claim moved, **in the same form Answer uses** — the typed subject references plus the discriminator. None of the four keys is dimension, proposition, card or attribute, so without this **replay cannot reconstruct the answers**, which is the invariant the answer–claim separation exists to make testable |

The four keys are also why **one stream rolls up three ways.** Person history, deal history, and account-level win and loss pattern analysis all read the same rows grouped differently. This is what makes account planning nearly free in a later version.

**Person Timeline**
The ordered set of claim rows for one Individual. What twenty-five Contact Map Details across two years collapse into. Retrieved by key, not by scan.

**Current-Deal Exclusion**
An invariant. Historical contention queries the person timeline **filtered to opportunities other than this one.** The system writes verdicts to the timeline by design, so without the exclusion it finds its own output in history and treats it as corroboration. Confidence would rise with no new evidence. This is the note self-reinforcement failure relocated, and here it requires an explicit filter rather than an absence.

**Calculated Insight, CI**
A batch-computed metric over historical data in Data 360, queryable from Apex. The mechanism for per-person aggregates: average sentiment across all prior appearances, proportion of deals where inside the inner circle. Cold-seeding and historical contention are both CI lookups against precomputed values, not scans.

**Library**
The permanent archive in Data 360. The transcript index as passages plus meaning-coordinates, the claim history in perpetuity, the decision log, and the calculated insights. Originals stay in customer storage, are indexed once, and are never copied.

**Warm Window**
How long claim rows live on core before retirement. Default 30 days, configurable. Storage rather than row count is the binding constraint, and storage allocation scales with license count, so a small org with heavy call volume reaches the limit before a large one does.

**Retirement**
The move of claim and candidate rows from core to the library once past the warm window. **Confirm-then-purge:** a core row is removed only after the library write is acknowledged, or the permanent record acquires holes.

**Reading memory from Apex**
Three supported paths: static SOQL against DMOs from API 61.0, `ConnectApi.CdpQuery` for SQL, and `queryCalculatedInsights` for aggregates. Batch Apex is blocked with QueryLocators but supported with Iterable. Two costs to meter from day one: SOQL against DMOs consumes Data Services credits, and the Apex must run in the Data 360 home org rather than an org merely connected to one.

## I. People and dimensions · gloss v2.1

Where the proposition model meets attributes that are not one bit.

**Dimension**
One attribute of a person on one deal's map. **The dimension set is discovered, not fixed**, and differs between account and opportunity level and between orgs.

**Four dimensions are live at opportunity level, not six.** Read from `ALTF__Contact_Map_Details__c`, which carries 38 fields:

| Dimension | **Label, which is the rubric** | Kind | Values | Filled |
|---|---|---|---|---|
| `ALTF__Status__c` | **Support** | Ordinal | Enemy → Non-Supporter → Neutral → Supporter → Mentor | 54.8% |
| `ALTF__Political__c` | **Political Status** | Ordinal | Outside → Political Structure → Inner Circle | — |
| `ALTF__Coverage__c` | Coverage | Deal-scoped ordinal | No Contact → Brief → Multiple → In-depth | — |
| `ALTF__Buyer_Role__c` | Buyer Role | Categorical | Approver, Decision Maker, Evaluator, User, Signature Approver | 40.0% |

**The labels are not what the API names suggest, and the label is the rubric.** `ALTF__Status__c` is labelled *Support* and `ALTF__Political__c` is labelled *Political Status*. Reading the API name instead of the label would put the wrong question to the model — and *Support* is the better question anyway, because it says what is being asked.

**Every map number needs a qualifier: the object serves both maps.** `ALTF__Contact_Map_Details__c` holds 40,259 rows, of which **only 18,577 are opportunity-scoped.** The rest are account-level. Percentages above are against the opportunity-scoped population.

**Every dimension carries an unknown slot natively** — labelled *Unknown* in this org — so `UNVERIFIED` did not have to be introduced. The philosophy's hardest requirement was already met by the schema. **The label on the slot is org-editable and is never matched**; the slot is identified structurally or by setup-time mapping. *Amended in v1.6 — see Verdict.*

**Dimension Kind**
Three treatments, and picking the wrong one breaks either the philosophy or the product.

| Kind | Treatment |
|---|---|
| **Ordinal** | **Cited delta**, plus or minus one from current state |
| **Categorical** | **Assertion proposition**: is X the Decision Maker, `TRUE` / `FALSE` / `UNVERIFIED`, with a span |
| **Deal-scoped ordinal** | Ordinal, but never inherits. Always seeds at the floor |

> **The ordinal row is withdrawn for ontology-backed dimensions.** *Corrected in v2.1.* Where an authored ontology exists — Support and Political Status carry guided questions — **the rung is computed from the authored propositions, and state is reconstructible from the contract answers**, not by summing deltas. Replay is unaffected; the mechanism differs. **The delta model survives as the inference fallback where no ontology exists.** The deal-scoped-ordinal row changes with it: Coverage no longer seeds at the floor, because it is answered by counting — see Cold Seed below. **[v2.5: for Support the mechanism moved again — the sentiment quiz is retired from extraction and the counter is re-promoted to Support's mechanism (Charters §P8.4); see The Counter's Return in the v2.5 section.]**

Which dimensions are ordinal is itself discovered, because value sets differ per org.

**Scoped-Out Dimension**
A dimension present on the object that the machine never writes, because the org's own metadata shows no rubric was built for it.

`ALTF__Decision_Orientation__c` is the only dimension with **no `_Answer__c` field**, meaning Altify never authored a path to a value for it. It is categorical, and it asks for a judgment about a person's character rather than a report of their speech. Absent a rubric there is nothing to discover, and under **Graceful Absence** a dimension with no rubric produces no propositions. **Humans only.**

**The adoption numbers support the scope-out for a better reason than neglect.** It is filled on **549 of 18,577 opportunity rows — 3.0%**, against 54.8% for Support and 40.0% for Buyer Role. But it is filled on roughly 5,500 **account-level** rows, ten times more. So it is not a neglected field. A person's decision orientation is a durable trait, and recording it once per person on the account map is the correct place for it. Scoping it out of per-deal work agrees with how the field is actually used, rather than overruling it.

*The UI labels this dimension* **Adaptability** *rather than Decision Orientation, and displays it prominently in the contact panel. Field label and displayed label diverge, which is worth remembering wherever we quote a dimension name back to a seller.*

> **Marked wrong in v2.1 — that note implied one field with two labels, and they are two different fields on two different objects with different value sets.** `ALTF__Contact_Map_Details__c.ALTF__Decision_Orientation__c` is **deal-scoped** — Financial / Technical / Relationship / Business, 3% filled — and is the field this entry scopes out. **`ALTF__Contact__c.ALTF__Adaptability__c` is person-durable** — Innovator / Visionary / Pragmatist / Conservative / Laggard. Both remain out of scope; the conflation does not. The two-tier person split behind this is Object Model's.

**Relationship Owner**
`ALTF__Contact_Map_Details__c.ALTF__User__c` — a plain User lookup on the map row, added later than the four dimensions. Filled on **15,367 of 18,577 opportunity rows, 82.7%**, across only 13 distinct users.

**Filled more diligently than the methodology itself, which is diagnostic.** Support sits at 54.8% on the same rows. Nobody records who owns a relationship more carefully than whether that person supports them, so the 82.7% is almost certainly a default rather than a decision — likely the row's creator or the opportunity owner. One join confirms it.

There is **no constraint at the data layer**: a plain User lookup, not required, no filter. Account Teams and Opportunity Teams are not enabled in this org, so the picker cannot be gated on either; whatever narrows it is UI logic, most plausibly licence assignment.

> **The hazard is invisible rows.** If the picker filters and we write a User it would not have offered, we create a row the seller cannot see or edit. **Human precedence survives in principle and breaks in practice — nobody can override what they cannot see.** So: only ever write a User the interface would itself have offered.

This is the mechanism working correctly rather than an exception to it. The scope-out was read off the schema, not decided by us, and an org that did build a rubric for it would get propositions automatically.

**Derived Dimension**
A field on the map that looks like a dimension, is computed by Altify from another dimension, and **must never be written.**

`ALTF__Is_Key_Player__c` is computed from Political — verified empirically, with a contact at Political Structure reading `true` and a contact at Outside Political Structure reading `false`. `ALTF__Color__c` is derived from Status. `ALTF__Sibling_Sort_Order__c` is layout.

Writing a derived field either fails or produces a value that Altify's own recalculation will contradict. Key Player is therefore not a proposition and not a charter output. It moves when Political moves, which is the only correct way for it to move.

**Note Capacity Is Shared**
`ALTF__Note__c` on the map row is 1,024 characters **for the whole row**, not per dimension. Four dimensions and one citation budget between them. Citation payload must be allocated, and a long span on Status can starve Buyer Role of anywhere to record its evidence.

**Delta**
A cited movement of plus one, minus one, or zero on an ordinal dimension from its current state. One proposition per person per dimension rather than one per possible value. No evidence means zero, means no write, which keeps **Absence Never Establishes** intact. State is reconstructible from the journal by summing deltas, each carrying its own citation.

> **The last sentence is withdrawn for ontology-backed dimensions.** *Corrected in v2.1, alongside Dimension Kind above.* For Support and Political Status the rung is computed from the authored propositions and **state is reconstructible from the contract answers.** The delta, and its reconstruction-by-summing, survive as the **inference fallback** where no ontology exists.

Movement of more than one rung is permitted where structure compels it. A person established as both Decision Maker and Approver is necessarily inside the political structure, so the political dimension may move more than one step, because the inference is structural rather than sentimental.

**Cold Seed**
The initial population of a relationship map for a new opportunity, before any evidence exists on that deal. Sourced from Calculated Insights over the account's history: who has appeared on prior opportunities of this type, and what their aggregate position was.

**Prior**
A seeded value. **A prior is not an establishment.** It has no citation on this deal, and under **Citations Do Not Cross Deals** it cannot have one. It marks the zero point of the ladder. The first cited delta from this deal's own evidence is the first establishment.

**Attenuation**
Seeded ordinal values regress one rung toward neutral. A historical Mentor seeds at Supporter; a historical Enemy seeds at Non-Supporter. History informs, and pays a rung for having been earned somewhere else.

> **Marked wrong as a universal in v2.1 — seeding is now per dimension.** **Support resets to Neutral** rather than attenuating, because its questions are about *this deal's solution* — and Altify proves the point by authoring a separate account-map set that asks about the *provider* and *your company*. **Political carries under a one-year recency bound**, configurable, inheriting from the Evidence Contract. **Buyer Role never seeds**, unchanged. **Coverage needs no seed**, because it is answered by counting every conversation regardless of deal. The one-rung regression above survives only as the fallback shape for an ordinal dimension with no per-dimension rule of its own.

Categorical dimensions are never seeded. Role is set by evidence on this deal or not at all.

### Personas, and the people who are not there yet · gloss v2.1

**Persona**
A required role on a deal's map that no identified person occupies. Held on `ALTF__Relationship_Map_Persona__c`, 14 fields, parented to the standard Opportunity.

**Ghost**
How a persona renders on the map: a placeholder card in the shape of a person, with no person in it.

> **A ghost is the rendering of an unverified gating proposition.** It is not a lightweight record type or a UI convenience. *This deal requires a Decision Maker and we have not identified one* is a binary proposition about this opportunity, currently `UNVERIFIED`, and the ghost is what that verdict looks like on a map. Every rule that governs propositions governs ghosts, including **Absence Never Establishes** — a ghost never resolves anything, it only shows that nothing has.

**Graduation**
The disappearance of a ghost when a real person on the same map carries the matching persona value.

**Graduation is a live value-match join.** Established empirically, not inferred: creating a persona made a ghost appear; setting the matching value on a real contact made it disappear; removing the value made it reappear. Across all three steps the persona record's `LastModifiedDate` still equalled its `CreatedDate` and the map row was untouched. **Nothing is created, nothing is deleted, and the whole thing is reversible.**

> **The consequence is the single strongest argument for owning an object.** Because graduation writes nothing, Altify holds no record that a gap ever existed, and no record of when it closed. A deal that ran six months short a Decision Maker and finally found one looks, afterwards, exactly like a deal that never had a gap at all. The history is not hidden. It was never written.

**Fulfilment Record**
Ours. One row per persona per opportunity, recording that a gap opened, how long it stood, what closed it, and when. The only possible home for the history graduation destroys, and the source of *missing persona count* and *oldest unaddressed red flag age* on the roll-up record.

**Personas Never Seed From History**
A ghost is a deal-local target, not a fact about a person. That a role was filled on a prior opportunity says nothing about this one, and seeding one would manufacture a gap nobody has evidence for. Only real people carry priors across deals, and only attenuated.

**Full Rubric Seeds, Stage Flags**
Ghosts are seeded from the **full rubric**, never from the stage-filtered live set. A map showing only the people needed at today's stage is a to-do list; a map showing everyone needed by close is a target. **Stage governs when a ghost begins to flag, never whether it exists.**

**Persona Vocabulary**
A shared managed global value set, used by both the persona record and the contact. **Restricted by default**, so off-list values cannot be written from Apex — which makes it a genuine **Closed Vocabulary** enforced by the platform rather than by us. Subscribers may add values and additions survive package upgrades, so it is discovered at runtime like any other vocabulary and never shipped.

> **The vocabulary is currently less precise than the rubric that must express itself in it.** The core assessment proposition names Approvers, Decision Makers, Evaluators and Users — verbatim, and identically to the `Buyer_Role` picklist — and **none of those four exist in the persona value set**, which is almost entirely job titles and is being used as one. A rubric that asks for a Decision Maker cannot raise a ghost for one until the value exists.
>
> ***Almost entirely job titles* is corrected in v2.1: the twelve values are two job titles and ten personifications.** The precision gap above stands unchanged — the four rubric roles are still absent — but the characterisation of what fills the set was wrong.

This is a setup-time gap, not a runtime one, and it is resolved by adding values rather than by writing code. Values must be grounded in verbatim question text and nothing else — if no proposition names the role, the role does not belong in the set.

**Persona, as carried on the contact**
*Added in v2.1.* `ALTF__Contact__c.ALTF__Altify_Personas__c` — a multipicklist of the twelve persona values, **account-durable across every opportunity** under that account, because `ALTF__Contact__c` is the person-durable tier of the two-tier person model while `ALTF__Contact_Map_Details__c` is the deal-scoped tier. This is the write target of the People charter's persona emission. **The machine only ever adds and never removes**, which dissolves the cross-deal collision the field would otherwise create, and **projection resolves a detected divergence by union rather than by contention — the only target where that is true**, because the field is additive and both values are true. Distinct from **Persona** above, which is the required-role record that renders as a ghost; the contact-carried value is what graduation matches against. The write path and the no-new-key argument are Object Model's; the projection rule is Architecture's.

**Gap Visibility**
The product concept that a described-but-unfilled requirement is itself a deliverable.

Four times now, in four unrelated places, the same shape has turned up: Altify can already describe what a winning deal looks like, and almost nobody has filled it in.

| Surface | Describes | Filled |
|---|---|---|
| Personas on the map | Which people the deal still needs | 11 of 62 |
| Solution cards from line items | What we are actually selling | 3 of 94 |
| Level of Relationship | Current against desired relationship depth | 77 of 207 |
| Insight card to objective linkage | Which account objective a deal insight serves | 3 rows in the org |

Naming it once prevents rediscovering it per object and then solving it four different ways. **The gap is the product.** The system's output is not a filled field, it is the visible difference between what the methodology requires and what the deal has — and the visibility has to survive the gap closing, which is what the fulfilment record is for.

## J. Insights and solutions · gloss v2.0

Insights are not unstructured. Of everything on an insight card, only three fields are free text; the rest is enumerated, boolean, or a typed pointer.

**Insight Card**
One note on the insight map. `ALTF__Type__c` is the row: Goal, Pressure, Initiative, Obstacle, Solution, discovered rather than assumed. Free text is confined to short description, long description, and impact.

**Insight Section**
A column on the map, org-authored and freely renameable. Ordered by `ALTF__X_Coordinate__c`. Scoped to an account, optionally to an opportunity.

**Owned Section**
A single section, created if missing per opportunity, into which the machine writes every card it creates. Placed at maximum X plus one.

This is a **write boundary made spatial**. Human sections are never touched, which extends human precedence from field level to layout. Uninstall is one delete. Coverage is legible at a glance. And a human who moves a card out of the owned section into their own has performed an acceptance gesture that requires no new interface, because the move itself makes the card human-authored.

Consolidated, never dated. Dated sections multiply without bound and would force deduplication to search across all of them.

**Insight Proposition Families**
Four, every one binary, every vocabulary discovered.

| Family | Proposition |
|---|---|
| **Existence** | A card of type T covering this substance exists on this deal |
| **Attribute** | This card's priority is High. This pressure is Financial |
| **Link** | This contact is an Informer of this card. This contact is an Owner |
| **Edge** | This card causes, drives, or addresses that card |

Confirmation is not a family. It is the verdict state, written to Altify's own `ALTF__Confirmed__c` with `ConfirmedBy` and `ConfirmedOn`, which already supplies absent, present-unconfirmed, and confirmed-by-a-named-human.

**Causal Edge**
`ALTF__Insight_Card_Edge__c` is the methodology's causal chain and runs its full length: pressure into initiative, initiative into obstacle, obstacle into solution. The target field is named `ALTF__Solution_Insight_Card__c` for historical reasons and does **not** mean edges terminate at solutions. Observed rows include Pressure to Initiative and Initiative to Obstacle.

A standing example of why the architecture reads metadata rather than trusting field names.

Edges are section-scoped, so edge proposals are bounded to cards within one section rather than the whole map.

**Grid Position Is Presentation**
`X` and `Y` on the card-section junction are layout. Causality lives in edges. The machine proposes type, section membership, and edges. **It never writes coordinates.**

**Bounded Deduplication**
An insight card is an entity the machine may create, so *does a card covering this already exist* has to be answered. Similarity would be inference, so instead the candidate is compared one at a time against existing cards of the same type on the same account: *is this quote about the same thing as this card, yes or no.* Each comparison is a binary proposition with a citation, verified like any other.

Bounded by construction. Insight maps hold tens of cards, so a candidate costs a handful of comparisons. No embeddings, no similarity thresholds, no vector index.

**Solution Card**
Two kinds, established differently.

| Kind | Established by | Citation | Cost |
|---|---|---|---|
| **Linked** | An opportunity line item, through `Product2.ALTF__Solution__c` | The line item record | Free, state-established, no model |
| **Unlinked** | Someone discussed something not on the quote | Verbatim span, which becomes the card title | Normal extraction path |

The catalogue is never used as a vocabulary, because at enterprise scale it is one. Line items are, because a deal carries a handful.

The title of an unlinked card is the **verbatim span truncated to the field limit**. Never a machine-authored name, because a name is prose.

**Solution Provisioning**
*Parked, recorded for later.* Where a product carries no Altify Solution, one can be created deterministically from a discovered grouping key on the product, and the card created against it. This removes the manual duplication that is the observed reason the feature goes unadopted.

Three constraints if it is built. It is a **setup operation, not a runtime one**, because a solution is reference data with a different lifecycle from deal data. The write to the standard product object must be **separable and toggleable**, since product masters are frequently locked or externally synced. And it is subject to the **cardinality guard**: a CPQ quote with thousands of lines must roll up to a handful of themes or abstain, never create one card per line.

**Solution Coverage**
The set difference between line-item solutions and linked solution cards, computed in Apex. Missing cards are **created silently and not flagged**. Flagging a gap the system just closed itself is noise, and on observed data the gap is near-universal: of 94 line-item solution pairs on open opportunities, 3 had a corresponding card.

The reverse direction, a mapped solution never quoted, is recorded and not flagged in v1.

### Criteria · gloss v2.0

*Added in v1.4. Reasoning and the org findings are in Object Model.*

**Criterion**
A condition our solution must meet, stated by the buyer. Distinct from an insight, which states something about the buyer's world — their goals, obstacles, pressures, and the initiative behind the deal.

*They run a security review* is an insight. *Must pass InfoSec* is a criterion.

> **A stated goal does not create a criterion.** A goal of 3% revenue uplift is an insight. It becomes a criterion only when someone says we must prove it. **This ships as a seed non-establishment rule rather than being learned**, because a model holding both taxonomies will manufacture criteria out of goals and will do it plausibly every time.

**Criteria are emitted by the insight charter.** Unbounded text is that charter's shape. Two charters reading one transcript would both fire on the same sentence with nothing to arbitrate. **[v2.5 note: superseded as placement — decision criteria join People (Charters v2.5 ruling, contracts at §P8.5); the boundary and seed rule below stand.]**

**A criterion persists for the life of the deal and is never satisfied by us.** It is a standing fact about what a person weighs. Sending a document is our action, not their confirmation, and the speaker requirement means only they can confirm it. There is no satisfaction field and we do not add one.

**A criterion never raises a flag on its own**, because it is discovered from evidence rather than declared in the customer's rubric, and letting it flag would be the machine deciding what is do-or-die. `ALTF__Required__c` — labelled *Mandatory* — is the **human promotion lever**, and only a promoted criterion may flag.

**Criterion Holder**
The person a criterion belongs to: whose decision it bears on and who must be satisfied. **This is what projects into Altify**, whose own junction asks *who is this decision criteria important to* and carries no type field.

**Criterion Informer**
Whoever told us the criterion exists. Usually the same person as the holder. Where they differ — *my boss John will not take a call until he has ROI documentation* — **John is the holder and Sarah is the informer.**

**The informer does not project.** Their identity lives on the Claim as the speaker of the citation, because provenance is what Altify's fields were never built to hold. **Never encode an informer's name inside criterion text**: it cannot be joined or reported, and the holder's own call preparation would show nothing.

A buyer reporting a colleague's criterion is strong evidence — they are describing their own company's decision process. A *seller's* note claiming the same thing establishes nothing about the colleague, per **Speaker Requirement**.

**Criterion Provenance**
Altify's Formal and Informal type, and it is **provenance rather than intensity.** Formal means the criterion is already on paper: the RFP, the requirements document, the scorecard. Informal means nobody wrote it down — the personal win, the executive burned by a vendor last year. How forcefully someone states a criterion says nothing about which it is, so the type is set only when the speaker says where the criterion came from, and otherwise left empty. **Intensity has its own home in the Mandatory flag.** **[v2.5 note: DC-F's typing axis is RULED provenance (Matthew, 4 August): organizational standing spoken makes Formal, else Informal, upgradeable — Charters §P8.5.]**

## K. Flags, guidance, contention, and demotion · gloss v2.1

**Flag**
A raised item requiring human attention. A flag is never a score.

**A flag belongs to the deal, never to a person.** *Added in v1.6.* Anyone on the opportunity team writes to that deal, so a flag can never be attributed to whoever last touched a record, and no surface may show who raised one or who left one standing. *This is the sentence that stops somebody building a who-broke-this view.* **Provenance changes who gets asked. It never changes whether the flag fires**, and it is not a property of the flag.

**Guidance**
*Added in v1.6. Used across the whole set since v1.5 and never defined here, which is a gap in the file that is authoritative for vocabulary. Placement and the surfaces are in Architecture.*

Everything the system offers a seller that is not a flag. Non-gating propositions, stage qualifiers, a person's own recorded criteria, what to raise with whom. **Assembled at the moment of a ritual — a morning brief, a call preparation, a debrief — and never pushed.**

**The distinction is push against pull, and it is the whole of it.** A flag is a demand: it arrives as a Task, it counts, it ages, it wants clearing, and it comes looking for you. **Guidance is an offer.** Making it a flag type imports the flag lifecycle — raised, aged, escalated, cleared — and **that lifecycle is precisely the machinery that nags.**

**Guidance is derived and holds no state.** Recomputed at each ritual from the live set and the current deal position. Persisting it would create a second source of truth that goes stale between being written and being read. **The act of surfacing is recorded** — what was shown, in which ritual, on which deal, when — on the **Surfacing** object, because *does surfacing change behaviour* is unanswerable forever if it is not written at the instant it happens.

> **Guidance may infer, and this is a ruling rather than a tolerance.** *Added in v1.6.* The whole architecture exists to keep inference out of the record, and then guidance selects one person from twelve and orders what to say. **The resolution is that guidance establishes nothing.** It writes no value, it carries no citation of its own, and it points at claims that carry theirs. **Inference is forbidden where it would write and permitted where it only suggests.**
>
> **What changes is not whether judgment happens but what it operates on.** Every input to a recommendation was verified once with a quote attached, so a bad recommendation is traceable to the specific established facts it used. That is inspectable in a way retrieval-derived guidance is not — and it is a narrower claim than *our guidance is right*, which is the version that would not survive contact with a customer.

**Rendering**
*Generalised in v1.6 from an entry that named the Task specifically.* Any surface presentation of a flag: a line in a brief, a component on the record, an assistant's message — and, if that write is ever ruled in, a standard Task.

**State flows from the flag to its renderings and never back.** Completing, dismissing, editing or deleting a rendering clears nothing, because any gesture on a rendering that cleared a flag would be a dismiss button under another name — the Task's Completed checkbox is the canonical example, tickable by anyone, at any time, for any reason. A gesture on a rendering is read as a **disposition** at most: a recorded signal that a human engaged, carrying an evidence watermark, never an establishment. The flag clears when its cause does, and the flag clearing closes its renderings. **The flag is the record and it lives on our object.**

> **Whether standard Tasks are a rendering is reopened in v1.6 and is not settled.** Earlier versions asserted it as decided, and that decision was never actually taken. Creating a Task involves no trigger — the trigger ruling is untouched — but it is a **write to a native object we do not own**, and that class of write must be designed toggleable per customer, exactly as projection is, before it ships. Until that design exists, flags render on our own surfaces only. The attraction that made the Task the assumed answer survives unchanged, which is why the question is open rather than closed: a Task arrives wherever the seller already works, including a headless assistant.

**Red Flag**
**One severity, and it is maximum.** A red flag means the deal cannot be treated as closeable until resolved. It persists until the proposition is established or a human overrides it. Acknowledgement does not clear it.

Causes: a proposition established `FALSE`; a gating proposition not yet established; contention on a gating dimension such as a disputed budget holder or decision maker.

The causes differ. The severity does not.

**Day-One Red**
**Every gating proposition is red from the moment the opportunity opens.** *Ruled in v1.6.* Not at a threshold, not once a model has looked. A necessary condition that has not been met is not met, and a brand-new deal has met none of them.

**This dissolves the abstention-versus-flag-volume tension.** The worry was that honest abstention inflates reds and makes a careful system look like a failing one. It cannot: **the flag was already red before the model looked.** Abstention leaves a flag standing rather than raising one. The ceiling is set on day one and the only direction is down.

> **Which flips the metric, and the metric is the product's own scoreboard.** Not *how many reds does this deal have* — that number is highest on the newest deal and says nothing. It is **how many has this deal cleared, against how far through its runway it is.** Same underlying count, read the other way. The difference between an alarming product and a work list is entirely which direction it is read in.

**No completeness score.** *Retired as a concept, not merely as a flag type.* Incompleteness is the loudest thing on the screen by construction, so a number describing it adds nothing. The only question ever asked is whether the things that will kill this deal are still true.

**One residue, and it is display rather than design.** A deal where the model abstained on everything looks identical to a deal nobody worked — both sit at full red. **The evidence-considered timestamp on the flag distinguishes them**: evidence considered and nothing cleared, against no evidence at all. The decision log distinguishes them a second time, for anyone reading reasoning telemetry rather than a deal.

**No Dismissal**
There are exactly two ways a red flag clears: evidence establishes the proposition, or a human sets the value directly and owns the risk in writing. **Acknowledgement is not one of them.**

A dismissible flag teaches sellers that flags mean nothing, and a system whose warnings can be waved away is worse than no system, because it manufactures false confidence while the forecast stays wrong.

**Human Override Does Not Retire The Proposition**
A human answering a flag settles the current question. It does not stop the proposition being evaluated, because a proposition that can be overturned by reality must keep being assessed. A human marking budget confirmed in March must not silence the system when the buyer says in June that the budget was pulled.

Nagging is prevented by the **evidence watermark**, not by retirement: the same evidence never raises the same flag twice, while new evidence always speaks.

Retirement applies only where **truth-decay class** is permanent. There is nothing left to re-evaluate, so a human answer settles it for good.

**Machine-Resolved Flags Remain Re-Flaggable**
A seller who clears a flag by making a call, where the outcome lands in a transcript, has produced a **machine** establishment. Actor is `MACHINE`, so demotion applies and the flag can be raised again if circumstances change. Only a direct human write carries human precedence. The distinction is carried entirely by the actor stamp and needs no separate rule.

**Yellow Flag**
*Defined under **Ratification** below. **The entry that stood here until v1.6 was the retired one** — it described a non-gating completeness item, which is now **Guidance** and is not a flag at all. v1.5's changelog said that entry was replaced; it was added beside it instead, and this file carried two Yellow Flag definitions saying different things. Removed rather than amended.*

**Green Flag**
**Positive contention.** Current state is worse than history says it should be. A person recorded as non-supporter today who has been supportive across several prior deals is not a defect, it is an opening, and the flag carries guidance: raise the prior history and repair the sentiment.

> Contention runs in both directions. Negative contention, where history is worse than the current record, is red. Positive contention, where history is better, is green. Same mechanism, opposite polarity. Most systems only look for the bad news.

**Missing-Relation Flag**
*Added in v2.1. Placement and reasoning are in Architecture.* A flag type keyed on **deal plus relation kind**, rolling up and naming the specific rows inside it, cleared only when the count reaches zero, no dismissal. **Built general — the class does not know what a Solution or a Pressure is. The count is the headline and the members are the work.** First instance: a Solution card with no edge to any Pressure or Obstacle, which fails Altify's own published definition of a Solution, since three of its four admission questions are about links to other cards.

**Escalation Threshold**
The point at which a standing red flag becomes urgent, expressed as a percentage of expected time to close rather than an absolute duration.

> **What this governs changed in v1.6.** Under **Day-One Red** the threshold no longer *raises* the flag — the flag is already open. It governs **when the flag escalates**: when it surfaces as a Task, when it enters the seller's brief, and when its age starts counting against the deal. **Escalation is red-flag age against elapsed runway.** The machinery is unchanged and what it drives is not.

**The denominator is Altify's derived close date and never the Opportunity's.** The Opportunity close date is seller-editable, so a threshold keyed to it clears by pushing the date out, which is the dismiss button in another costume. `ALTF__Calculated_Close_Date__c` and `ALTF__Weeks_To_Close__c` are derived and cannot be typed.

| Proposition source | Threshold binds to | Why |
|---|---|---|
| Assessment criterion | **Phase** | Already exists in org metadata and already implies sequence |
| Sales process qualifier | **Stage** | Qualifiers are already stage-mapped natively |
| Any | Per-proposition override in the evidence contract | Available, never required |

Derived from the org's existing plan-type and time-to-close configuration rather than invented. `ALTF__Weeks_To_Close__c` and `ALTF__Calculated_Close_Date__c` are the confirmed starting points.

**Evidence Clock**
Fires immediately on an establishment of `FALSE`. Raises red on a proposition that had cleared, and holds red on one that had not.

**Maturity Clock**
Fires when the elapsed fraction of expected time to close passes a proposition's escalation threshold while the proposition is still unestablished. **It escalates a standing red; it does not raise one.** *Changed in v1.6 — under Day-One Red there is nothing left for it to raise.* Non-gating propositions have no clock, because they are guidance and guidance is pulled.

**Historical Contention**
A check of a newly written verdict against the person timeline, excluding this opportunity. **Runs after the write**, because it requires the journal to have streamed to memory.

For ordinal dimensions this is rung arithmetic in Apex: current state minus historical aggregate, against a threshold. Free, replayable, no model.

**Insight Contention**
Contention over unstructured content, for example a stated purchase driver against the account's historical buying pattern. There is no ladder to subtract, so this requires a model. Runs on a schedule rather than in the write path.

**Pattern Contention**
*Added in v2.1. Placement and reasoning are in Architecture, where contention is ruled to split three ways.* Contention from **authored queries over the memory plane at grains beyond sentiment** — **written once by a model at setup, frozen, executed by Apex**, the recipe-ruling shape. Setup-time because Calculated Insights are immutable once shipped, and a model inventing aggregates at runtime would fight that wall nightly. Ordinal contention is integer subtraction with no model; insight contention is semantic and takes a model on a schedule; pattern contention is the third kind.

**Demotion**
The reversion of a verdict to `UNVERIFIED`, in either direction, when contention fires. Citations are kept in place. A contention flag attaches carrying the proposition and answer record identifiers so a human lands on the record itself rather than a description of it.

**Demotion applies only where the contested value was written by the machine.** Where a human authored it, nothing is demoted and only a flag is raised. Demotion and flagging are separate mechanisms, and a flag never implies a demotion.

A demoted proposition carries an **evidence watermark**: the same evidence can never re-establish it. Only newer evidence, or a human setting the value, clears it.

**Human Override**
A human may set a demoted or contested value directly. The system does not prevent this. It records that contention was surfaced, what it consisted of, and who accepted it.

> The system's obligation is to identify the contention, not to win the argument. Once contention is surfaced and recorded, the risk of proceeding belongs to the human who accepted it. That transfer is only legitimate because it is written down.

**Reconciliation**
The one human surface in the product. A session, headless and ad hoc or scheduled with a group, in which a human and the system walk the open flags together. Altify's existing Test and Improve is the scheduled form; the headless form is the same activity reached from a morning brief or an assistant, and it is not a separate architecture.

**Disposition**
A human response to a flag, recorded with an evidence watermark so the same evidence never raises the same flag twice. A disposition records that a human engaged; it does not by itself establish the proposition. The response itself re-enters as evidence.

### Ratification · gloss v2.0

*Added in v1.5. Placement and reasoning are in Architecture.*

**Ratification**
A write that has passed every check and is waiting for a human to permit it. **The fifth gate and the only one a human operates.** No autonomy level permits a write that failed a check and none removes a check — level 1 is the same system with a human at the end.

**Ratification gates model-established claims only. Two classes pass the gate at every level, including level 1.** *Ruled in v1.6.*

**State-established claims.** Ratification exists so a human can check machine inference before it writes, and a state-established claim involves none — *decision team named* is Apex counting Buyer Role values, and the arithmetic is replayable by the customer themselves. There is nothing to second-guess, so holding it is not caution, it is delay. This is the principle applied honestly rather than a concession to make level 1 tolerable, and it means **a level-1 customer gets the computable half of the methodology working on day one with zero approvals.** *How much of the rubric that covers is unmeasured and should be established before it is relied on.*

**Decision criteria.** Ruled directly. A criterion is an additive row with its citation attached for inspection; it collides with no existing human value, it never raises a flag on its own, and its whole worth is being visible on the person it belongs to at the moment of call preparation — a gate would hold back exactly that. One consequence lands free: criterion claims are live on commit, so the *Formal Decision Criteria* predicate reads identically at every autonomy level.

**Bypassing the gate bypasses nothing else.** Both classes still pass verification, and evidence-established criteria still pass blind re-adjudication. The only thing skipped is the human at the end.

**Yellow Flag**
*This entry replaces the v1.4 definition, which described a completeness item.* The flag type raised when a candidate has passed verification and blind re-adjudication and the active autonomy level holds its class. **A gate, not a notification.** It **never escalates to red**, because a pending approval is not a deal defect.

**Yellow measures the org's autonomy setting, not the deal**, so it never enters the same counter as red on a leadership surface. A seller's brief may show both; a risk ranking shows only red.

**A yellow clears itself when a human does the work by hand.** *Added in v1.6, and human precedence forces it rather than permits it.* A held write whose value a human has since set directly would now overwrite that human's value, which is forbidden — leaving the flag open asks permission for something the system is not permitted to do. The same poll that detects human edits withdraws the candidate. Two cases: the human wrote what was proposed — withdrawn silently; the human wrote something else — withdrawn, and it becomes contention. **Neither is an approval and neither is recorded as one.** Which sharpens what an unapproved backlog means: sixty open yellows are not approved, not declined, **and not done by hand either.**

**Persistent non-approval routes to whoever owns the rollout, never to whoever owns the number.** *Added in v1.6, with its reasoning, because the reasoning is mechanical rather than philosophical:* the moment a seller believes a manager sees their approval count, they approve in bulk without reading. **That erases the denial record — the only evidence of whether the machine was wrong — and converts a safety gate into a rubber stamp. The autonomy ramp is earned on that record, so destroying it makes level 3 unearnable.** Red-flag age already tells a leader a deal is not being worked, without watching the person.

**Publication State**
The field on the **Answer** — and on the Candidate, where a decline lives — recording whether the value is live. **The claim is written regardless; only its effect waits.** *Corrected in v2.0 — the old sentence put the field "on Claim", which was the retired naming; the field tables place it on Answer and Candidate.*

**Settled in v1.6 as one axis: held is not live for anything.** Not projection, not satisfying its condition, not a state-established predicate's count, not contention's historical aggregate, not the roll-up, not guidance. One filter, applied by every reader, silent when forgotten — which is the stated cost, and it is the second filter of that defect shape after current-deal exclusion. The reasoning that settled it is in Architecture.

**Held Write**
An answer whose publication is waiting on a human — the claim that moved it is written regardless. **Held candidates stay on the candidate ledger and never queue on the mirror**, which upserts and would overwrite the first of two. **A held answer does not satisfy its condition**, or approval is theatre. **Held is live for nothing** — not projection, not condition satisfaction, not a predicate's count, not contention's aggregate, not the roll-up, not guidance.

**And it is invisible to every predicate that counts answers.** *Added in v1.6, and it falls out of what a citation is rather than out of policy.* A state-established proposition cites state — the rows that satisfied it, each carrying its own citation — and a held answer is not state; it is a pending write. Counting it would cite a row that is not there, and the two-hop chain from proposition to row to the words someone said would dead-end on its first hop.

**The verdict therefore moves with the autonomy level, and that is correct rather than tolerated.** A level-1 customer bought a system in which nothing is true until they say so, and a predicate that ignored their gate would make approval theatre from the other side. The rule that stands unchanged is narrower than v1.5 stated it: **a predicate counts our live answers and never Altify's projected records**, because projection toggles independently of ratification, and an org with projection off would read empty at every level.

**Decline**
A human's refusal to publish an establishment. **Not an establishment of the opposite.** The condition returns to `UNVERIFIED`, the maturity clock keeps running and the red flag fires on schedule — which is what stops Decline being a dismiss button, and why declining makes the seller's position worse rather than easier.

**A declined write is data.** The candidate survives, carrying what the machine believed, its citation, its charter version and the fact of refusal, on one row — which makes approved and declined writes comparable against deal outcomes. *Corrected in v2.0 — this said the claim survives, and it was wrong: a decline establishes nothing, writes no claim, and lives on the Candidate and nowhere else.*

## Terms added 3 August 2026 · glossary v2.3

**Charter designation.** The field on Evidence Contract naming which charter owns the question. Written by the contract seeder and the coming reconciler, read by the applicable-set resolver, never read by any charter. A contract with no designation is legacy and resolves only under Process, deliberately.

**Declared applicable set.** The contract set a pass actually hands the model: declared per charter at the pass, resolved per charter's own rule (assessment per deal via the configuration chain, People per roster), never the org-global population. The org-global read survives for inventory and display only.

**Ceiling derivation.** The Political Status derivation model: placement is a ceiling over accumulating establishments, never a contest between them. Properties accumulate and never subtract; the map value is the highest placement standing establishments support; exit happens only when words flip a two-sided question. Contrast with Support's ladder, where recency arbitrates opposing sides.

**Membership never routes.** The resolver law that a person's presence on any number of maps contributes nothing to routing. Resolution is per Source to at most one deal and one account, plus affirmatively named content stretches; ambiguity abstains and nothing writes.

**Contract reconciliation.** The ingest-time step, owed and not yet built, that reads the live rubric per declared charter per resolved deal, matches against existing contracts by content hash, and mints or supersedes contract versions where the rubric changed. Contracts stay frozen identity; the reconciler is what keeps them current without breaking the receipt chain.

## Terms added at v2.4 · 3 August 2026

**[v2.5 note: the pass-shape terms in this section — Extract-Bind-Verify pass, Inventory, Binding, Verification stage — are SUPERSEDED as the pass by Charters §P8 (the pairs shape, the family sweep) and stand as the vocabulary of a retained history. Evidence budget, Computed coverage and the `model_missed` rate survive with their scope adjusted: `model_missed` as a rate is additionally bounded by the inverted-grading ruling — misses are a list, never a denominator, where grading is inverted.]**

**Extract-Bind-Verify pass.** The pass shape (Charters §P7.3): one strong-model read per Source emitting an inventory; binding promoting Candidates to Claims; separate smaller-model verification by coextension before any Claim writes. Successor to every per-proposition and per-person pass shape, all retired.

**Inventory.** Stage 1's output: every charter-relevant statement in a Source — speaker, subject person, line anchor, minimal verbatim span, plausible proposition families. Potential claims, no verdicts. The inventory is the Candidate layer's content.

**Binding.** The promotion step from Candidate to Claim: deterministic fan-out from families to the subject's contracts in the declared set, plus a small transcript-free call per pair needing judgment — establishes, does not establish, insufficient.

**Verification stage.** The blind reader as a load-bearing stage, not a check: a separate, significantly smaller model seeing only claim and quoted evidence, judging coextension (subject, scope, quantity). A verification fail writes the Candidate with its reason and no Claim. Gated once by an adjudicated comparison against the strong model before the small model is trusted.

**Evidence budget.** ~90 output tokens per finding. Justified by coextension — the shortest span that still carries subject, scope, and quantity needs room — never by display. Stored quotes on Answer rows remain full-fidelity from stored text regardless.

**Computed coverage.** Coverage is presence per occasion per scope, occasion = scope + artifact hash, counted deterministically; optional decay is parked config. Never extracted from words; the coverage proposition family does not exist in any read.

**`model_missed` rate.** The per-run reported rate of statements the single read did not catch, measured at adjudication. Under extract-once this is a chosen, bounded residual — reported beside findings and abstentions, never buried.

## Terms added at v2.5 · 5 August 2026

*The pass vocabulary, from Charters v3.0 §P8, Model & Flow v1.4, and the Board's 5 August rulings. Defined here and nowhere else.*

**Pair.** Call 1's atomic output: a question from the declared set, the verbatim words that answer it, and the meaning those words voice. No person attached — identification is call 2's. True-or-nothing, in the question's own direction. Fact families (Political, Buyer Role, criteria, Process, assessment) add a coverage reading, full or partial, with partial the instructed default under doubt; sentiment has no partial. The verbatim string byte-locates in the frozen artifact or the pair is discarded and counted.

**Initial row · Identified row.** The pair ledger's two persistences, built as `AAO_Pair__c` with an explicit `Located`/`Identified` stage picklist (Model & Flow v1.4). The initial row is call 1's output as found, unowned; **its byte-located verbatim string is the anchor** — no separate anchor entity exists. The identified row is call 2's identification, linked to the initial row; it is what call 3 verifies and what the gates promote toward Claim. Two rows so every stage is measurable in isolation; the `run|ref|stage` unique index refuses more than one and cannot detect zero, so `assertOneForOne` ships beside it.

**Run receipt.** One row per Source per pass: read on this date, by this charter version, these calls made, these pairs found, these claims written. The did-we-read-it record and the whole replacement for abstention rows; feeds the flag's last-evidence-considered timestamp. **Owed by CODE (§P8.0), and its load rises under the family sweep**: four reads per pass make a partially completed pass expressible, and the receipt is what records which family reads ran.

**Sentiment read.** Call 1's direct reading of words into one of the five states — mentor, supporter, neutral, non-supporter, enemy — under the label meanings pinned as law at §P8.4. Whole, never partial: partial sentiment is the second-guessing the quiz retirement killed. No neutral label exists; words that voice no stance produce no pair. **Engagement is not stance** (questions, process talk, "key step" praise emit nothing) and **courtesy is not stance** (the graded trap: "Looking forward to it" is niceties, not support).

**The counter's return.** The re-promotion of the sentiment counter from inference fallback to **Support's mechanism** (Charters v2.7, arithmetic refined at v2.8, §P8.4). One clamped integer per person, −3 to +3, rungs at fixed positions. Each distinct verified establishment moves it one in its direction; a call's movement is the net sum; the only caps are the clamp and the ceiling of the strongest state the evidence voices — supporter-grade tops at +2, mentor-grade reaches +3, symmetric below. **Terminals are proof-gated, never time-gated.** Explicit declarations jump with the sequence flagged; mixed evidence nets with every quote journalled; movement applies to the standing counter read at reconciliation; replay over claims in evidence-occurred order reconstructs it exactly. Its field home is owed from CODE's proposal (Model & Flow v1.4).

**Family sweep.** Call 1's shape, ruled by Matthew 5 August: **once per declared family, not once per transcript** — four bounded reads of the whole artifact, each carrying exactly one family's question set and nothing else. The cost law's exact terms: crossing by PERSON is forbidden because it scales with the roster without bound; crossing by FAMILY is permitted because it is bounded at four or five and scales with nothing — not roster, not length, not density; the code asserts the call count is never a function of participant count. What it bought, measured: **attention** (sentiment 2 → 11 pairs under one unchanged contract), tripled stable output, and multi-establishment landing structurally — one utterance pairs independently in several families' reads. Charters v3.0 §P8.1 is the charter text; the two-halves stamp composes per family read.

**Regression set.** The standing successor to the recall gate, ruled 5 August, built by CODE at 27 assertions. **Every establishment Matthew has graded PASS is a standing assertion on every run; every graded trap must not appear; correct refusals are neither** — asserting one asserts that call 1 must keep making a mistake call 3 can catch. Keyed on **contract plus byte-range intersection** against the frozen artifact, never the stored string. An undeclared family reports `UNREACHABLE` on its own line and can never inflate a recall failure. Findings state their nature — counts, never a rate whose denominator is the harvest. **Temporal validity is owed** (adjudication sheet v0.7): an assertion is meaningful only forward from the run it was graded on; run against a pre-grading run the set reports false regressions.

**The third state.** The family of run reports that refuse a false binary, because **a binary verdict on an incomplete pass must lie about one of the two cases.** Members: **`INCOMPLETE`** — `assertOneForOne` could not complete the arithmetic; reports its counts and is scored as neither held nor broken; **`UNREACHABLE`** — the regression set's line for a family undeclared in this run, never counted as a recall failure; **`CHANGED, undiagnosed`** — a difference observed without an attributed cause. The principle: name the state rather than forcing the binary; expect more members as instruments grow.
