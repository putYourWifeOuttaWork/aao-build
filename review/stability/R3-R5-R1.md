## R3 · THE FINALIZER, AND IT IS PROVED RATHER THAN TRUSTED

The hundred-tenth stamp attached a condition: *"One sandbox proof per the capability law before
trust."* Here it is, and it is the whole point of the item.

A queueable attached `AAO_RunFinalizer`, then burned the SOQL governor. The transaction was
killed outright; the catch inside `AAO_PassQueueable` cannot reach that class and never ran.
**The receipt carries the leg anyway**, written afterwards in the finalizer's own transaction:

```
RCPT-00000035  stages=1
"stage":"R3 PROBE",
"error":"The transaction was killed and could not journal its own failure; this leg was
         written afterwards by the run finalizer.
         System.AsyncException: System.LimitException: Too many SOQL queries: 201"
```

**That is the 16 August failure made visible.** `Too many SOQL queries: 101` killed the s5 join,
39 upheld pairs produced zero claims, and nothing anywhere said so - because a stage that leaves
no leg and a stage that never ran are the same fact from outside. They are no longer.

**One thing the probe caught about its own output**, and it is why probing beats assuming: the
governor numbers on a finalizer leg are the FINALIZER'S transaction, not the dead stage's, so
they read near zero on a leg whose stage died of a governor. The leg now says so in words on the
row rather than leaving a reader to misread it.

**The probe class and its receipt row were both removed.** The quoted bytes above are the record;
a probe artifact standing on a real deal's receipt list would only ever mislead.

## R4 · A FAILED INGEST IS A ROW NOW, NOT A DEBUG LINE

The swallow stays and is still right: the artifact is stored and immutable, one lost adjudication
re-runs, and a thrown exception would take every other Source in the batch with it. What changed
is that its only output was `System.debug`, visible for exactly as long as somebody is watching a
log - which on the async path is never.

Failures now route to `AAO_Receipt.recordFailure` under `ingest|<sourceId>`, so a Source that
failed and a Source that found nothing are finally different facts. **Written after the loop, not
inside the catch**, and that ordering is load bearing: `AAO_Pipeline` documents its own
callout-before-DML ordering, and a receipt leg is DML, so writing one inside the catch would put
DML in front of the next Source's callouts and turn one Source's failure into every later
Source's failure.

### The defect R4's own test found

`recordFailure` **silently wrote nothing when the Source could not be read.** The receipt's
`AAO_Source__c` lookup is refused for an absent row, this class's standing swallow ate the
refusal, and the leg vanished - so the one case where a receipt matters most, a Source that could
not even be read, was the one case that left no trace. The lookup is now dropped when the Source
is unreadable; `AAO_Receipt_Key__c` carries the id as text, so nothing is lost.

**Second time the swallow-everything telemetry policy has hidden a defect** (the sixty-eighth
stamp recorded the first, and recorded the cost as accepted). It is the accepted cost being paid
again, on schedule.

## R5 · THE RUN LEASE, PROVED ON STAGE A

`AAO_Run_Lease__c`, one object, two keyed row kinds. **The unique index is the lock**, not a guard
on one: two passes racing both insert `HOLD|<opportunity>` and the index refuses the loser. An
acquire that read first and then branched would hand the deal to both, because both readers see
an empty table before either commits - the one shape where read-before-write cannot be the
answer, and the reason this is the system's only lawful `DUPLICATE_VALUE` branch. The
hundred-sixteenth stamp's alarm governs accrual state, which accrues and has a read it could have
made; a lease has neither.

Measured on STAGE A, live:

```
first acquire            = true
same-run re-acquire      = true      (the chain crosses transactions on one lease)
second run acquire       = false     (refused by the index, enrolled instead)
third run acquire        = false
waiting rows after enrolling one of them three times = 2   (one per source, not four)
release by a run that does not hold it -> holder unchanged, still r5-first
```

Then the drain, and this is design's correction to R5 doing its work:

```
r5-second-later   enrolled FIRST, carries the LATER conversation
r5-third-earlier  enrolled second, carries the EARLIER conversation

DRAIN handed to = r5-third-earlier
```

**Arrival order would have woken the first. The conversation's clock woke the second.** A lease
serialises; the law orders. The queue then drained itself to `holder=NONE waiting=0
totalLeaseRows=0` with no residue and no wedge.

### Why R3 had to land first, in one line

A run that dies holding the lease wedges the deal forever, and only a finalizer runs after that
death. **The release is on death ONLY**, not on every stage: the pass crosses one transaction per
stage on one lease, so a finalizer releasing every time would hand the deal away mid-pass and let
a second run interleave - the exact race the lease exists to stop, reintroduced by the lease's own
release.

### One door closed while wiring it

`AAO_PassQueueable.execute` returned immediately at `stage == S_DONE` **without releasing**.
Unreachable on the chain today, but the drain wakes a run at whatever stage its waiting row
recorded, and a stale one landing there would hold the deal forever with nothing running. A wedge
is the one failure this mechanism exists to prevent, so it does not get a back door.

## R1 · THE CAP IS DERIVED AGAINST THE WALL THAT ACTUALLY FAILS

Mined every verify callout the org has on record - 17 of them across `wf-s3`, `wf-s4`, `wf-s5`,
`pf0813-uphold`, `em0813-stack-c1`, `em0813-stack-c2`.

```
largest callout that SUCCEEDED    82,213 ms   (68 claims, wf-s5)
observed death                   ~88,000 ms   (hundred-thirteenth stamp, 120,000 ms timeout set)
```

**The wall sits inside a 5,787 ms band**, and 88,000 is the number we have actually hit. Budget at
the standing 75% headroom: **66,000 ms**.

### The finding is the variance, not the slope

A least-squares fit over the 17 gives `ms = 1303 * claims + 2629` and it is close to worthless:
residuals span +21,258 to -9,039 ms, and **three calls of identical size, 12 claims each, took
15,287, 25,462 and 39,526 ms** - a 2.6x spread at fixed input.

So the cap derives from the **worst measured rate, 3,294 ms per claim**, never the average one:

```
median rate (1,322 ms/claim) -> cap 49    <- larger than the 47- and 68-claim calls that died
worst  rate (3,294 ms/claim) -> cap 20
```

A cap from the median would have permitted the exact shape this whole line of work came from.

### AND THE HONEST RESULT: GRAMMAR STILL BINDS, AT 15 AGAINST TIME'S 20

`MAX_UNITS_PER_KEYED_CALL` is now written as the minimum of two independently measured ceilings -
the compiled-grammar 400 at ~22-24 units, and the gateway's response wall in time. **Today grammar
binds and R1 changes no number.**

That is the derivation's result rather than a reason not to have made it. A cap ASSERTED to be
safe and a cap MEASURED to be safe are different facts, and only one survives the corpus growing.
At the binding cap a call reaches `15 x 3,294 = 49,407 ms`, **56% of the measured wall** - the
first time this project can say that sentence about the wall that actually fails, rather than
about the 120,000 ms ceiling every previous timing table reported against.

### The wall measures itself from here

A cap derived once from seventeen receipts is a cap that was right about yesterday's corpus. Every
callout past the 66,000 ms budget now marks its leg with `wallWarning`. **It marks and never
fails**: a slow call that RETURNED is a success, and calling it an error would be a lie on the
process bar. What it produces is a queryable count of how often we approach the wall - the number
the next derivation needs and the one nobody has ever had. With R3 in place, a callout that DIES
on the wall now leaves a leg too, so both tails get measured.

### WHAT I DID NOT CHANGE, and it is a real open item

**`AAO_Timeout_Ms__c` is still 120,000 while the wall is ~88,000.** A dead call therefore waits
32 seconds past the point it can never return. Lowering it looks obvious and is not: the largest
SUCCESSFUL call on record is 82,213 ms, so at the old unsharded call sizes there is almost no room
between "slow but will succeed" and "will never return." **At the capped size the worst observed
call is 39,526 ms, so a much lower timeout becomes safe** - but the timeout is org configuration
under the BYO-LLM law, and trading one failure mode for another is not mine to do quietly. Named
for design rather than changed.

## THE OWED LINE FROM THE HUNDRED-EIGHTEENTH, and it is not the confirmation it asked for

> *"`AAO_Retire` also carries a `rebuildVerdicts` path and was not in the named list - confirm it
> reads through the supersession chain (or is out of answer scope), one sentence in the next
> report."*

**It calls `AAO_PairCommit.rebuildVerdicts` itself, so it read whatever that method read - and
that was only half the chain.**

The join hands in CANONICAL rows, because read-before-write makes them the rows it wrote, and the
merge walked DOWNWARD from there. **Retirement hands in whatever answer the retired claim points
at, and a superseded row's claims are exactly what a reconciliation leaves behind.** Such an id
resolved nothing walking downward, then fell out at the `AAO_Superseded_By__c = null` filter - so
retiring a claim on a superseded row rebuilt nothing at all, and the canonical row kept a verdict
built on a receipt that had been withdrawn. Silent, and precisely the divergence retirement exists
to close.

Fixed inside `rebuildVerdicts`, so one implementation covers both callers rather than
`AAO_Retire` growing a second: one extra query resolves a given id upward to its canonical. One
hop is the whole walk, because `AAO_Project` selects its canonical `WHERE AAO_Superseded_By__c =
null`, so a pointer can only ever target a canonical row.
